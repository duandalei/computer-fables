谱

一树千丁

—— 一个关于“把一族人放进一棵树”的故事

徽州府南的汪村，汪氏一族传到第十九世，丁口一千二百，是县里数得着的大族。

族里有一本老谱。谱是手抄的，一卷一卷，按世代排：第十八世有某某、某某、某某。名字底下只记一行小字，生辰、葬地，再往下就没了。谁是谁的儿子，谱上不写；谁家绝了后，谱上也不划。修谱的规矩是三十年一修，修的时候把旧谱誊一遍，添上这三十年新生的丁。

誊谱的人图省事，只见名字不见人。添丁的人家报了名，他就在“第十八世”那一行末尾添一个名字；死了人的，他翻不到那一页，索性不添。几修下来，谱上的人越来越多，路却越来越乱。

那一年冬至祭祖，出了两桩事。头一桩，第三房和第五房各有一个“汪世荣”。执事照谱摆牌位，把第三房的牌位摆到了第五房那一桌。两房的人在祠堂里吵了半日，差点动手。第二桩，村东一户人家绝了嗣，田归了族里，可谱上那家的名字还挂着；分胙肉的时候，族里照谱分了一份，领肉的人家不认，说这户早没人了。

族长在祠堂里坐了一夜，第二天托人从府城请来一位修谱先生。

谱师来了，先不修，只翻谱。翻了七日，把谱合上，说：这不是谱，是一本名册。名册只记“谁在这一代”，不记“谁从谁来”；人一多，就分不清谁是谁家的。

族老问：那该怎么修？

谱师取一张纸，画了一个人，底下画四条线，线上各挂一个人，再往下分。他说：

“谱要成树。一族只有一个谱根，便是始祖；谱根往下，一房一支，支下再分房，房下才是丁。

每一个丁，只挂在一个人下面——他的父亲。

挂在谁下面，就是谁的儿子；从谱根往下走，走到他，只此一条路。”

族老们看看纸，又看看旧谱，半晌没人说话。第三房的房长先开口：这树一画，我们第三房和第五房的两个“汪世荣”，可就分得清清楚楚了。

谱师这才立谱例。

谱上每一条，叫一“丁”。一丁有一“格”，格里写名、字、排行、生辰、婚配、房份、谱号。格里字再多，也不算丁，不往下挂人。丁下挂的，才是子嗣。

谱号全族唯一，写在名字旁边，永不重复，也不许两丁共用一个。房份是“第三房”“第五房”这样的名目，许多人共用；辈分写在谱眉上，一代一片。

丁下除了子嗣，还有“旁记”——某年迁居、某年绝嗣、某年出继。旁记写在丁旁，不挂人，也不占一支。

族老问：谱号为什么要单立一样？名字不够用么？

谱师说：不够。名字会重，小名更会重；族里一喊“世荣”，站起来的可能有两个。谱号不会重。寻人先报谱号，一寻一个准；报房份，寻出来一串；报辈分，寻出来一大片；只报小名，多半要打架。

规矩定了，谱师开始修谱。他把各房送来的丁单一张一张归到树上：先找父亲，再往父亲底下挂儿子；父亲找不到的，先搁在一边，另造一册“待考”，等族老来认。

添丁也有添丁的次序。新丁先在“丁稿”上写全，写全了，再挂到父亲丁下；若要排在两个哥哥之间，得说明挂在谁之后，不能随手往末尾一塞。排错了次序，长幼就乱了。

除名不撕，也不涂。谱师在格里注一个“出谱”，再从父亲丁下把这一丁摘下来。摘下来的丁不烧，另收一匣；日后族里要查旧事，还能翻得到。

过继最费事。一个人从生父丁下摘下来，挂到嗣父丁下；一摘一挂，人还是那一个人，谱号不改。谱师说，一丁只能在一处；挂到了嗣父名下，生父那边就空了，不是另抄一份。

谱修到一半，族里议事，又出了岔子。

谱师抄了两份名册。一份留在自己房里，随修随改；一份抄给族长，摆在祠堂，供议事时翻。房长们很快发现：房里那份，族里一添丁，第二天自己就多一行；祠堂那份，抄的时候多少人，过后还是多少人。议事时有人说“谱上添了三个丁”，族长翻开祠堂那份，一个也没有，两下里吵了半日，才明白说的是房里那本。

谱师听说，把两份名册都收了回去，重新抄了一份，在封皮上写明“某月某日抄，此后添丁不在此册”。从此议事之前，先问一句：看的是活册，还是抄本？

族中议事，本来也有规矩。丁家有了事，先报房长；房长报支长；支长报族长。一层一层往上，叫“报”。族长若说一句“房内自了”，这桩事就到此为止，不必再往族老会上送。若族长要全族都知道，就在祠堂门口贴一张告示；各房的人自己来看，不必一家一家去说。告示一贴，一族的门都响。

也有急事反着来：族长先在会上发一句话，再一层一层往下问，问到最后，才听见各房回话。

谱师把这些也写进了谱例。他说，族里的事，最怕两头都听不见：一桩事报到了房长，房长压着不往上送，族长就以为族里太平；一张告示贴在祠堂，有一房的人偏不去看，事后又来问，也是白贴。

谱修成了，要送书坊刻版印书。

谱师对族长说：改谱与改版，是两回事。谱是活的，今天改一笔，明天又添一丁；版是死的，刻一刀是一刀。若每添一丁就重刻全谱，书坊非关门不可。

他改了法子。寻常改动只在谱上落笔，不动版；攒到下个月，取一张校样，把新旧两稿并排比对，只把真正改过的几行挑出来，交书坊挖补。改十处，若只动了三行，就只刻三行。改完再印，印出来的才是新谱；谱上改了、版上没改，翻书的人就还照着旧样看。

族老问：那谱上一有改动，岂不是要人人重看一遍？

谱师说：不必。谱是谱，书是书。谱在祠堂里，随族里改；书发到各房，是某年某月的谱。书的封底刻着日子，一看便知是新是旧。

后来族大了，各房也有各房的事：田产、坟山、私怨，不宜都写进总谱。谱师便许各房另立“支谱”，挂在总谱某一丁名下。支谱自成一本，有自己的谱根、自己的谱号；总谱上只看得见“某支有支谱一卷”，翻不进支谱里头去。支谱里的事，支内自己了，外房问起来，只说个大概。

总谱管总谱的，支谱管支谱的，两下里互不搅扰，也不至于各房把所有私事都摊到祠堂上。

谱成那日，族长领着各房看谱。从谱根往下，一支一支分下去，一千二百丁，各在各的位置上；谁的父亲是谁，一路上一目了然。

族长翻到最后，问：日后有在外经商几十年的族人回来认祖，只记得父亲的小名，你怎么替他找？

谱师指着谱根：

“从根往下走。父亲是谁，儿子就挂在谁下面；

一路走到他，只此一条路。

寻到那一丁，只改那一笔。”

祠堂的匾上，后来添了四个字：一树千丁。

文档对象模型

Document Object Model

这个故事讲的是 DOM（Document Object Model），中文常译作“文档对象模型”。浏览器读到一份 HTML（或 XML、SVG），不会把它当成一长串文字，而是先解析成一棵节点树：document 是入口，<html> 是根元素，head、body 是它的子节点，元素里再嵌元素；文字、注释也各是一个节点。DOM 就是操作这棵树的编程接口——查节点、读属性、添子树、摘节点、挂事件。它不绑定语言：JavaScript 在浏览器里用得最多，Java、Python、C# 也都有各自的绑定。故事里的谱根、丁、子嗣、旁记、活册、议事、刻版，一样一样，都是这棵树的规矩。

“文档对象模型”这个译名，拆开就是三件事：文档被解析成树，树上的每个点都是对象，而这套对象构成一个可操作的模型。端点时代的接口以字符串和动作为中心，DOM 则以结构和位置为中心：先找到那个节点，再只改那一处。

一树千丁：DOM 是什么

DOM 是浏览器把 HTML、XML、SVG 这类标记文档解析之后，在内存里建成的节点树，以及操作这棵树的一套接口。标准由 WHATWG 维护，语言无关：JavaScript 在浏览器里用得最多，Java、Python、C# 也都有绑定。要点是：DOM 既不是源码，也不是屏幕上的画面。源码里写 <p>你好</p>，DOM 里则是一个 p 元素节点，下面挂一个文本节点“你好”。脚本改了 DOM，页面随之变化，但“查看源代码”看到的仍是服务器送来的原文；反过来，脚本也能从零建一棵树，它并不对应任何源码。故事里谱师把名册重排成一棵树，正是浏览器做的事：先解析，再建树。DOM 树是活的：查询到的是当前的树，不是副本；改一处，后续查询立刻看得见。

谱根与丁：节点、属性与树

树上的每一个点都是节点。常见类型有 Document（整个文档，document 就是它）、DocumentType（文档类型声明）、Element（元素，如 <div>、<p>）、Text（文字）、Comment（注释）与 DocumentFragment（不在文档里的轻量容器）。节点之间有父子与兄弟关系：parentNode、childNodes、children（只含元素）、firstElementChild、nextElementSibling。元素上的 id、class、data-*、style 是属性（attribute），存在元素的属性表里，不占子节点——故事里“格里写名、生辰、房份，格里字再多也不算丁”，说的就是 attributes 与 childNodes 分开。元素之间还夹着大量空白文本节点，因为源码里的换行和缩进也算文本；用 children 或 firstElementChild 可以绕开它们。还要记住，浏览器解析并不逐字照搬源码：<table> 里缺 <tbody> 会被自动补上，错位的标签会被纠正，所以 outerHTML 未必等于你写的原文。节点也可以脱离文档单独存在：createElement 造出来还没挂上去时，它仍在内存里，可以改、可以再挂回；DocumentFragment 则用来攒一批节点，一次性插入，省去多次重排。

寻丁：查询、遍历与活册

从树里找人，常用几个接口：getElementById 按 id 找，命中唯一，速度最快；getElementsByClassName、getElementsByTagName 按类名、标签名找，返回集合；querySelector、querySelectorAll 接受 CSS 选择器，前者返回文档顺序里的第一个匹配，后者返回全部匹配。名字会重、小名更会重——选择器也可能一次匹配好几个；要唯一，就靠 id，或者用 querySelectorAll 之后自己确认。两类集合必须分清：getElementsBy* 返回的是活集合（live HTMLCollection），树一变，它跟着变；querySelectorAll 返回的是静态 NodeList，是调用那一刻的快照，之后添丁不会多出来。故事里房里的活册与祠堂的抄本，就是这两样；childNodes 也是活的。若还要往上找，closest(selector) 从当前节点沿祖先一路找到最近的匹配，matches(selector) 判断自己是否符合。遍历时优先用 children、parentElement 这类只含元素的属性，免得被空白文本节点绊住。查询本身要遍历树，写在循环里反复查同一批节点很浪费；一次查好、缓存起来，或者用事件委托避免逐个绑定。

添丁、除名、过继：修改 DOM

建节点用 document.createElement('li')、document.createTextNode('…')；挂进树用 append、appendChild、prepend、before、after、insertBefore、replaceChild；摘下来用 remove 或 removeChild。要留意：appendChild 一个已经在树上的节点时，它会被“移动”而不是复制，原位置自动消失——这正是故事里过继的道理，一个节点只能有一个父节点。摘下来的节点仍在内存里，只要变量还引用着它，就能改、能再挂回去。改内容用 textContent（纯文本，安全），慎用 innerHTML（会把字符串当 HTML 解析，可能执行脚本，是 XSS 的常见入口）；改属性用 setAttribute，改类用 classList.add/remove/toggle，改自定义数据用 dataset，改样式用 element.style。大量插入时，先把节点攒进 DocumentFragment 再一次性挂上，能少触发很多次重排；批量更新时也别在循环里频繁读写布局属性。cloneNode(true) 可以深拷贝一棵子树，但事件监听器不会跟着复制。

从房长到族长：事件与冒泡

事件在 DOM 里有三个阶段：捕获（capture）从 window 沿祖先一路向下到目标，目标阶段，冒泡（bubble）再从目标向上回到 window。addEventListener(type, handler, { capture: true }) 可以在捕获阶段监听，默认是冒泡阶段。故事里“丁报房长、房长报支长、支长报族长”是冒泡，“族长先发话再一层层往下问”是捕获。event.stopPropagation() 阻止事件继续传到别的节点，stopImmediatePropagation() 连同一节点上后面的监听器也一并拦住；preventDefault() 取消浏览器的默认动作（链接跳转、表单提交），与传播是两件事。event.target 是真正被点到的节点，event.currentTarget 是当前正在执行监听器的节点，做委托时全靠这两个区分。事件委托就是把监听器挂在共同祖先上，靠 target.closest() 判断点到了谁——子节点是后来加的也照样管用，正合祠堂门口那张告示。要注意不是所有事件都冒泡：focus 与 blur 不冒泡（可用 focusin、focusout），mouseenter、mouseleave 也不冒泡；子节点若调了 stopPropagation，祖先上的委托就收不到。滚动、触摸这类高频事件可以加 { passive: true }，告诉浏览器不会调用 preventDefault，换来更顺的滚动。

谱与版：渲染与虚拟 DOM

改 DOM 不等于立刻重画。浏览器把样式计算、布局（layout，也叫 reflow）、绘制（paint）、合成（composite）排成流水线，通常等到下一帧前才统一处理。一次改十处，可能只布局一次；但如果在循环里交替读布局属性（offsetHeight、getBoundingClientRect()）又写样式，浏览器会被迫同步布局，一次一次地算，这叫布局抖动（layout thrashing）。稳妥的写法是先读后写，或者把写操作攒起来，在 requestAnimationFrame 里一次提交；动画优先用 transform 与 opacity，它们可以只走合成层。虚拟 DOM 是另一层：框架在内存里维护一棵普通的 JavaScript 对象树，状态变了先生成新树，跟旧树比对（diff），算出最小的改动，再一次性打到真实 DOM 上（patch）。故事里“新旧校样并排比对，只刻改过的几行”，正是这个意思。虚拟 DOM 并不让单次 DOM 操作更快，它换来的是可声明的写法和成批的更新；真正的性能仍取决于改了多少节点、有没有触发布局。框架也各不相同：React、Vue 用虚拟 DOM，Svelte 在编译期生成细粒度的更新代码，Solid 一类信号方案直接绑定依赖。列表很长时，虚拟滚动比任何 diff 都管用，因为根本不渲染看不见的行。服务端渲染先输出 HTML 字符串，浏览器解析成 DOM 后再“注水”（hydration）挂上事件，首屏更快，但水合本身也有成本。

支谱：Shadow DOM 与组件

支谱的比喻对应 Shadow DOM：一个元素（host）可以挂一棵自己的影子树（shadow root），树里的节点与样式同外面的文档隔开。外面的 document.querySelector 穿不进影子边界（除非拿到 host.shadowRoot 再查），影子树里的 CSS 也不会泄漏出去；<slot> 允许外部内容插到指定位置，:host 选中宿主，::slotted() 选中插进来的内容。Shadow DOM 加上自定义元素（custom elements）与 <template>，就是 Web Components 的三件套。它和 iframe 不同：iframe 是另一份文档、另一套脚本环境，Shadow DOM 仍在同一份文档、同一个脚本环境里，只是包了一层作用域。React、Vue 的组件不是 Shadow DOM——它们只是函数与虚拟节点，样式隔离要靠 CSS 方案自己做。影子树适合做不受外部样式干扰的控件（日期选择器、播放器、第三方挂件），但也带来调试与可访问性上的额外工作；closed 模式不是安全边界，只是让 shadowRoot 拿不到而已。总谱与支谱各管各的，不等于互不相干：宿主元素仍然是总谱上的一个节点，影子树里的焦点、事件与布局仍会影响整页。
