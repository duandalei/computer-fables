回车之后

—— 一个关于“一次点击要经过多少手”的故事

这一篇不新起一个行当。前面几篇的规矩，都已经在各自的行业里立好了；这一篇把那些规矩合在一处，看一封信从动笔到回音，要走多少手。

临河镇有个做绸缎生意的商人，要给京城的客商传一句话。他在柜上写了“同福号”三个字，交给伙计。伙计先到问名处查门牌，问事处翻了总册、公会册、店家册，递出一张纸条：东字十七号。伙计照着门牌写信封，把信交到信局。信局把信裁成小片，每片写上“自临河镇，往东字十七号”，编上号，交给顺路的人。碎片到了京城，先到东字十七号的街口，再按院号送到柜台，收信的客商把碎片按号拼好，回了信。回信又走一遍来路。

商人只看见屏风上一行字，不知道这一行字过了多少手。伙计说：问名、门牌、指路、裁信、挂号、柜台，一样都不能少。商人问：少一样呢？伙计说：少一样，信就到不了，或者到了也拼不起来。

这一篇要讲的，就是这一行字背后的全程。

谜底

一次请求的全程

How the Internet Works

互联网不是一条线，而是一张网；一次请求也不是一次跳跃，而是一串分层协作。你在浏览器里敲下回车，看似只做了一件事，实际上经过了：解析网址、查名字、找路、建连接、加密封、发请求、跨过许多张网络、到达服务器、再原路返回、解析页面、渲染画面。这一篇把前面几篇串起来，按真实发生的顺序走一遍。

先记住一个总原则：分层与封装。每一层只解决一类问题，并在自己的数据外面套一层“信封”；到了对端，再一层层拆开。应用层写 HTTP，传输层加端口与可靠性，网络层加 IP 地址与路由，链路层加 MAC 地址与帧头，物理层变成电信号或光信号。中间的路由器只看网络层及以下，不关心里面装的是网页还是邮件。

应用层
HTTP、DNS、SMTP、WebSocket 等；TLS 通常夹在应用与传输之间，给 HTTP 加密
传输层
TCP、UDP、QUIC；负责端口、可靠性、流量与拥塞控制
网络层
IP、ICMP、路由协议；负责地址与逐跳转发
链路层
以太网、Wi-Fi、PPP、ARP；负责同一段链路内的帧传输
物理层
光纤、铜缆、无线电；把比特变成光、电或电磁波

一次请求的十二步

解析网址
浏览器拆开 URL：协议（https）、主机名（example.com）、端口（默认 443）、路径与查询参数；先查浏览器缓存、HSTS、Service Worker
查名字
DNS 解析：浏览器/系统缓存 → hosts → 递归解析器 → 根 → 顶级域 → 权威服务器；拿到 A/AAAA 记录，得到 IP
选出口
操作系统查路由表，选网卡与默认网关；同链路内用 ARP 找到网关的 MAC 地址
建连接
TCP 三次握手：SYN → SYN-ACK → ACK；双方同步序列号，协商窗口与选项
加密封
HTTPS 再做 TLS 握手：验证证书链、协商密钥、确认 ALPN（h2 或 http/1.1）；TLS 1.3 通常 1-RTT
发请求
HTTP 请求：方法、路径、Host、Cookie、Accept、User-Agent 等头；可能有请求体；HTTP/2 用二进制帧与多路复用
层层封装
HTTP 字节 → TCP 段（加端口与序号）→ IP 包（加地址与 TTL）→ 以太网帧（加 MAC）→ 比特流
出门与 NAT
家庭路由器做 NAT，把私有源地址/端口换成公网地址/端口；交给运营商接入网
跨网转发
运营商网络 → 互联网交换点（IXP）→ 骨干与其他自治系统；BGP 选路，逐跳查表，TTL 递减
到达服务端
防火墙、负载均衡、CDN 边缘；解封装到 TCP，按目的端口交给监听进程；应用处理请求，访问数据库/缓存
响应返回
状态码 + 响应头 + 正文；TCP 确认、重传、窗口控制；可能经过缓存、压缩、分块传输
解析与渲染
浏览器解析 HTML 成 DOM，加载 CSS/JS/图片（更多请求），构建渲染树，布局、绘制、合成；JS 继续修改 DOM

这张网由什么拼成

你家的小网
Wi-Fi、手机、电脑、智能设备；路由器做 DHCP、NAT、DNS 转发，形成一个私有网段
接入网
光纤、同轴、5G、DSL；把家庭或企业接到运营商
运营商网络
接入、汇聚、城域、骨干；内部用 OSPF/IS-IS 等协议，对外用 BGP 宣告地址段
互联网交换点
IXP：多家网络在同一处交换流量，降低跨网成本与时延
自治系统
AS：一个机构管理的一张网络；AS 之间用 BGP 按策略选路，而不是只看最短路径
内容分发网络
CDN：把静态内容放到离用户近的边缘节点；DNS/anycast 把用户引到最近的一处
数据中心
负载均衡、反向代理、应用服务器、数据库、缓存；对外只暴露少数入口
海底光缆与卫星
跨洲流量的物理载体；海缆故障会影响一大片区域，路由会尝试绕行

出错时，先看哪一层

名字查不到
DNS：域名拼错、记录没配、解析器超时、NXDOMAIN；先 dig 或 nslookup
连接被拒绝或超时
TCP/网络层：端口没开、防火墙拦截、路由不可达、NAT 映射缺失
证书报错
TLS：证书过期、域名不匹配、证书链不全、系统时间不对、SNI 缺失
返回 4xx
HTTP/应用层：路径错、未认证、无权限、限流、请求体格式不对
返回 5xx
服务端：应用异常、上游超时、数据库故障、过载
页面慢
可能是 RTT 长、丢包重传、拥塞、服务端慢、资源太多、渲染阻塞；要分段测量

封装：一封请求怎么被一层层包起来

你在应用层写下的 HTTP 请求，先被 TCP 当成一串字节，切成段，每段加上源端口、目的端口、序列号、校验和，成为 TCP 段；IP 再把每个段包上源地址、目的地址、TTL、协议号，成为 IP 包；链路层再把 IP 包放进以太网帧，加上源 MAC、目的 MAC，成为帧；最后网卡把帧变成电信号、光信号或无线电波发出去。到了对端，顺序反过来：网卡收帧、拆帧，IP 拆包、查地址，TCP 拆段、按序重组，HTTP 才看到完整的请求。封装的好处是每层只读自己那一层的头，不必理解上层的内容；代价是每一层都增加一点开销（头部、处理、排队）。MTU 限制单个帧的大小，包太大要分片；分片增加开销，所以现代协议常用路径 MTU 探测来避免。NAT、防火墙、负载均衡这些“中间盒”会在途中改写某些头，甚至拆到应用层再转发，这是分层模型的现实例外。

延迟从哪里来

一次请求的时间，大致由四部分组成：传播延迟（信号在介质里跑，光纤中约每秒二十万公里）、传输延迟（把比特推上链路，取决于带宽与包大小）、排队延迟（路由器/交换机的队列，拥塞时最不可预测）、处理延迟（查表、拆包、应用处理）。往返时间 RTT 是这四者来回的总和，ping 测的就是它。带宽时延积（BDP）等于带宽乘 RTT，表示“路上能同时容纳多少数据”；窗口小于 BDP，链路就跑不满。丢包会让 TCP 重传，重传至少多等一个 RTT；拥塞会让队列变长，时延上升；缓冲区太大又会 bufferbloat。优化网页性能，先量 RTT 与丢包，再看服务端处理时间，最后才看前端资源；把三者混在一起猜，通常会改错地方。

从 URL 到页面：浏览器做了什么

浏览器拿到 HTML 后，先分词、建树，得到 DOM；同时解析 CSS，得到 CSSOM；两者合成渲染树，计算布局（每个元素的大小与位置），再绘制、合成到屏幕。遇到 <script> 会阻塞解析（除非 async/defer），因为脚本可能改 DOM；CSS 也会阻塞渲染，因为页面不想先闪一下无样式的样子。图片、字体、样式、脚本都是额外的请求，可能并发，也可能排队。首屏之后，JavaScript 继续改 DOM、发请求、更新界面。所谓“页面打开慢”，可能是 DNS 慢、TCP/TLS 握手慢、服务端慢、资源太多、关键资源被阻塞、渲染太重，原因要分段定位，不能一句“网络慢”带过。浏览器缓存、CDN、HTTP/2 多路复用、HTTP/3、预连接、预加载，都是在这条链路上省时间。

TLS 与 HTTP 的几个版本

HTTPS 就是 HTTP over TLS。TLS 握手先验证服务器证书（证书链、域名、有效期），再用非对称密钥协商出一个只有双方知道的对称密钥，之后的数据用对称加密传；TLS 1.3 把握手压缩到 1-RTT，支持 0-RTT 恢复（但有重放风险）。证书由受信任的 CA 签发，浏览器内置根证书；证书错误通常不是“网站坏了”，而是证书过期、域名不匹配、链不完整或系统时间不对。HTTP/1.1 用 keep-alive 复用连接，但同一连接上的请求仍有队头阻塞；HTTP/2 在一个 TCP 连接上多路复用多个流，做了头部压缩，但 TCP 层丢包仍会让所有流一起等；HTTP/3 把可靠传输搬到 QUIC（跑在 UDP 上），每个流独立重传，解决了 TCP 层的队头阻塞，还支持 0-RTT。版本越高并不自动越快，还要看网络、服务端和缓存策略；HTTPS 里的 TLS 细节见《封匣》。

网络之网：没有中心，只有约定

互联网（internet）的字面意思就是“网络的网络”。它没有一台总开关，也没有一个总账本：地址由区域互联网注册机构分配，域名由 ICANN 体系协调，路由由各个自治系统用 BGP 互相宣告，流量在 IXP 与私有互联处交换。你家路由器后面是一个私有小网，运营商网络是一个 AS，云厂商、CDN、大学、企业各自也是 AS；它们之间有的是客户—提供商关系，有的是对等互联。BGP 选路看的是策略与商业关系，不是纯粹的最短路径，所以“网络上的最短路径”常常不是地理上最近的路。CDN 与 anycast 把同一地址部署在多地，让用户被路由到较近的节点；NAT 让大量设备共享少量公网地址；防火墙与负载均衡在入口处做过滤与分发。正是这种“各自管理、按约定互联”的结构，让互联网能在没有中央控制的情况下持续扩张。

为什么这套东西能长这么大

三个设计选择最关键。第一是窄腰：网络层只留 IP 一个公共协议，上面可以跑任意应用，下面可以接任意链路；新应用不必改网络，新链路不必改应用。第二是端到端原则：网络中间只负责转发，可靠性、加密、语义放在两端；这样中间设备可以简单、快速、可扩展，创新也不必等全网升级。第三是尽力而为与分布式路由：网络不承诺质量，只承诺尽力；出了问题，路由可以绕行，应用可以重试。代价是：安全、可靠、低时延都要另外做，故障定位也更难。理解这三条，就能理解为什么互联网既能容纳几十亿设备，又经常让人“明明网络是通的，网页就是打不开”。

读法：从这一篇往回看

如果你是第一次系统了解互联网，建议按这个次序读：先读《碎成一百片的信》理解“为什么要切碎、为什么共享”；再读《门牌与指路簿》理解“地址与下一跳”；然后读《一封挂号信》理解“可靠性怎么补出来”；接着读《按名索址》理解“名字怎么变成地址”；最后回到这一篇，把十二步连成一条线。再往后，读《明码点菜》看应用层的 HTTP，读《封匣》看 HTTPS 里的 TLS，读《一树千丁》看浏览器如何把响应变成页面，读《认格不认人》看接口如何组织资源。每一篇只讲一段，合起来才是全程；不要指望一篇寓言把整张网讲完，也不要因为一篇讲得深，就以为它讲的是全部。
