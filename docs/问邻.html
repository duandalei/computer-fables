问邻

—— 一个关于“不必问遍所有人”的故事

青溪县尺牍库按“色”排信的法子，用了三年，库里攒下了十万张色卡。一张色卡是一封信的配方，颜色相近，说明信里说的事相近。陆先生很满意，阿砚却先撑不住了。

每天来查旧信的人不少。有人拿一封新信来，问：“库里有没有和这封讲同一件事的？”阿砚便要把新信染成一色，再一张一张地比：比过一万张，要半天；比过十万张，要五天。他试过让三个书吏一起比，可书吏们比到后来，眼睛都花了，常常把相近的颜色看错。

陆先生算了一笔账：十万张色卡，一封信来就要比十万次；若一天来十封信，就是一百万次。库里的旧信还在年年增加，这样下去，尺牍库迟早会被“找信”拖垮。

阿砚去请教顾师傅。顾师傅正在染一缸极难的秋香色，听完只说：“你比颜色，比的是‘谁离谁近’。这事我帮不了你，你去问驿站的周先生。”

周先生是青溪县驿站的“路簿先生”，一辈子只做一件事：画路。县城一万多户，他给每家画一张门牌，又在城门口立几块路牌；路牌不写每一户，只写“往东门大街”“往南门码头”；大街口再立巷牌，巷口再写门牌。外乡人进城，先看城门路牌，再看街口巷牌，最后按门牌找人家，不必从城门一家一家问过去。

阿砚把“找色”的难处说了。周先生笑了：“你这不是找色，是找路。十万张色卡，每一张都是一个地方；颜色相近，就是地方相近。你要找离新色最近的那几张，不必从第一张问到最后一张，只要先找几个‘地标’，再问地标的邻居。”

他给尺牍库画了一本“邻里簿”。

第一层只留几十张“地标色卡”，彼此隔得远，像城门、码头、大庙；第二层多留几百张，像城里的大街；第三层再密一些，像巷口；最底下一层，才是十万张色卡，一张挨一张。每一张色卡，除了记自己的颜色，还记下几个“颜色最相近的邻居”；上一层的地标，则往下指向几个下一层的入口。

查色的时候，阿砚不再从第一张开始。他先看第一层几十张地标，挑出与新色最相近的一张；再顺着这张地标往下走，走到下一层，问它的几个邻居：“你们谁离新色更近？”谁更近就往谁那里走；走到一个邻居都不比当前更近时，再往下一层。如此一层一层往下，最后停在最底下一层的一张色卡上，取它和它附近的几张，便是候选。

陆先生问：“这样找，能保证找到最像的那一张吗？”

周先生摇头：“不能保证。路簿是给人走的，不是给神仙算的。走得快，就可能错过一条小巷。”

阿砚起初不信。他拿一百封旧信来试：先把每封信从库里抽出来，再让邻里簿去找。结果九十九封都找回了原来那一张，只有一封找回了“第二像”的一张。两张的颜色差得极小，信里说的也都是“秋粮入仓”，只是年份不同。

陆先生问：“差一张，要紧吗？”

阿砚把两张信都读了，摇头：“不要紧。可要是查的是官司、契纸，差一张也许就要紧。”

周先生便教他调簿子。每张色卡多连几个邻居，路就密一些，找得准一些，可簿子也厚一些，走起来慢一些；每层多看几个候选，也更准一些，可一次查色要多花些工夫。阿砚试了半个月，定下一个折中：大多数查信够用，遇到要紧的官司，再让他多问几家邻居。

又过了些日子，库里新收了一批信。阿砚把新色卡插进邻里簿：先给它找几个最近的邻居，再让邻居们也把它记上；旧卡撤掉时，路也不能断，要把它从邻居的簿子上划去。若是改动太多，周先生便让他把整本簿子重画一遍——重画虽慢，却最干净。

有一年，顾师傅换了一种新的染色配方。阿砚按新配方把所有旧信重新染了一遍，邻里簿也得重画。周先生看着满屋的新色卡，说了一句：“路簿不造地方，只记地方之间的远近。地方挪了，路簿就得跟着挪。”

从此，尺牍库找信，不必再问遍十万张色卡。先问几个地标，再问地标的邻居；邻居的邻居，便是答案。

谜底

向量索引

Vector Index · HNSW · ANN

这个故事讲的是向量索引（vector index），更具体地说，是近似最近邻检索（ANN，Approximate Nearest Neighbor）中的一种经典结构——HNSW（Hierarchical Navigable Small World）。

有了 embedding，文本变成了向量；可向量一多，逐个比较就太慢。向量索引要解决的正是这件事：不保证每一次都找到“绝对最近”的那一个，但用少得多的比较次数，找到“足够近”的一批。故事里的“邻里簿”就是索引，“先问地标、再问邻居”就是图上的贪心搜索。索引只负责找得快，不负责理解意思；向量从哪来，是〈染字成色〉里 embedding 模型的事；索引存在哪、谁来管，是〈一库三役〉里向量数据库与索引引擎的事。

为什么需要向量索引

如果有 N 个向量，每次查询都逐个算距离，就要做 N 次比较。N 小的时候没问题；N 到了几十万、几百万，查询就会慢到不可用。向量索引用额外的内存和建索引时间，换更少的查询比较次数。它不改变向量本身，也不改变“谁和谁像”，只是把“找近邻”这件事做得更快。

HNSW 是怎么走的

HNSW 把所有向量组织成一张多层图。最上层节点很少，边很长，负责“先走到大致正确的区域”；越往下节点越密，边越短，负责“在小范围内精细地找”。查询从最上层的一个入口开始，在当前层反复走到离查询向量更近的邻居；走到没有更近的邻居时，下降到下一层，以当前点为新入口继续走。到了最底层，候选池里最接近的几个点就是结果。它像一张可以逐层放大的地图：先看省界，再看县城，再看街巷。

参数与取舍

M 决定每个节点连多少邻居：越大，图越密，召回率通常越高，内存和建索引时间也越大。efConstruction 决定建索引时的候选池大小：越大，图的质量越好，建索引越慢。efSearch 决定查询时的候选池大小：越大，召回率越高，查询越慢。工程上通常先定一个可接受的延迟，再在这个延迟下把召回率调到目标值。故事里“差一张要不要紧”，问的其实就是业务能接受多大的召回损失。

索引不是模型，也不是数据库

索引是数据结构，负责“找近邻”；embedding 模型负责“生成向量”；向量数据库负责“存向量、存原文、存 metadata、持久化、增删改查”；索引引擎负责“建索引、维护索引、执行查询”。HNSW 只是索引的一种实现，此外还有 IVF、PQ、DiskANN 等。不要在概念上把它们压成一个东西，否则排查问题时很难判断到底是模型、索引还是存储出了毛病。

工程细节

第一，距离度量要统一：建索引和查询必须用同一种度量，项目里用的是 cosine。第二，向量要先归一化，尤其是用 cosine 时。第三，索引是派生数据：原文、分块和 metadata 才是根；索引坏了可以重建。第四，记录 id 最好确定：项目里用 item{item_id}_chunk{chunk_index}，重索引时 upsert 覆盖，避免重复。第五，collection 的维度通常由首批写入锁定；换模型、换维度，就要新建 collection 或重建索引。第六，ANN 不是“差不多就行”的借口：召回率掉了多少、哪些查询会漏，要有评估。
