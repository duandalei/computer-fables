封匣

—— 一个关于“让不该看的人看不见”的故事

临江楼的掌柜，自从菜条被人抽走、改价、冒充跑堂之后，关了三天门。菜条的规矩他不想改：跑堂不认人，一天翻三百桌，全靠这张条子。可条子明着从大堂上过，谁都能看、能改、能接。他最后想明白：菜条本身没有错，错在它没有一只匣子。

他从府城请来一位做匣子的老师傅。老师傅看了三天，说：你要的匣子，得办三件事——别人看不见，别人改不了，客人得认得出这匣子真是你临江楼的。三件事缺一件，匣子就是白做。

掌柜的问：先做哪一件？

老师傅说：先做锁。

锁是一把对锁。客人取匣，先把自己的锁锁在匣上，送到柜上；柜上打不开，便再加上自己的一把锁，原样送回；客人开自己的锁，再送回去；柜上开自己的锁。四趟走完，匣里留下一把只有这两把锁配得出的临时钥匙。此后不论传多少张菜条，都用这把钥匙开匣关匣。

掌柜的看明白了：这把钥匙从没在匣外露过面，送匣的人手里只有锁，没有钥匙；就算匣子被人截了，没有两把锁，也打不开。

老师傅又说：一把钥匙不能用到老。一顿饭吃完，钥匙当场作废；下一顿来，重新对一次锁，配一把新的。这样即便哪天有人偷到了一把旧钥匙，也打不开今天的匣子。

第二件是封条。匣子合上，沿口贴一道封条，封条上压着老师傅的私印；谁要半路撬匣，封条必断。客人接匣，先看封条；封条断了，匣里的菜条一概不认。

第三件是验印。每只匣底都刻着“临江楼”的字号；可字号谁都会刻，对门黑店一天能造十只匣子。所以字号旁边，还得盖一枚商会的验印：商会先查实这家字号确有其楼，才在匣底落印。母印收在商会柜上，从不外借，纹路里藏着只有商会才知道的暗记；旁人照着描，描得再像，细处也对不上。

商会门前挂着一本验印证样。客人取匣，先看匣底：字号是不是“临江楼”，验印与证样合不合得上。两样都对，才能认定这只匣子真是临江楼的。客人自己家里也有一本“根册”，记着商会的母印模样；证样若换了，根册一对，便知真假。

黑店的人再来，抽走匣子，打不开；半路换一只匣子，匣底字号对不上，客人当场就不点了；冒充跑堂在门口接匣子的，客人先问一句“匣底字号”，他答不上来。

老师傅还留了一手：万一临江楼自己把钥匙给了别人，或者匣子被撬开、母印被仿，商会便把那一枚验印从门前的证样上撤下，再贴一纸告示。客人当日来对，一看便知，今天还能不能在这儿吃。撤下来的旧匣子，哪怕封条完好，也不再作数。

封匣的规矩立起来，临江楼的生意照旧红火。有客人问：匣子封着，是不是就说明这家店童叟无欺？

掌柜的摇头：匣子只保三件事——菜条没被人偷看，没被人改动，对面接匣子的确是临江楼。至于临江楼给的鱼新不新鲜、账算得对不对，匣子管不着。

又有客人问：那要是临江楼自己把钥匙给了别人呢？

掌柜的说：所以验印要由商会盖。哪天查出临江楼私配匣子、把客人的菜条往外递，商会便把验印撤下。匣子能保的是路上，保不了店里。

有外乡人不解，问掌柜：从前菜条明着递，也吃了十几年，何苦费这些事？

掌柜的把一只封好的匣子摆在柜上：

“从前是大堂里人人都长着眼睛，只是没人说破。

菜条还是那张菜条，规矩还是那套规矩；

多的只是一只匣子——让该看的人看得见，不该看的人看不见。”

老师傅在旁边补了一句：匣子不是护身符。它只保这一路；到了店里，菜新不新鲜，还得看掌柜的良心。

后来府城的酒楼都换上了封匣。大堂里再没有一张明写的菜条，跑堂还是不必认人，客人还是不必寒暄，一桌菜照样上得飞快。

TLS

Transport Layer Security

这个故事讲的是 TLS（Transport Layer Security，传输层安全协议）。它夹在应用协议与传输协议之间：HTTP 的请求与响应一个字不改，整段交给 TLS 去封；收到之后再拆开，交给 HTTP。TLS 只做三件事——机密性（别人看不见）、完整性（别人改不了）、身份认证（客人认得出对面真是临江楼）。HTTPS 就是 HTTP over TLS；邮件、即时通讯、VPN 也都能套 TLS。

要把 TLS 和 HTTP 分开看：HTTP 规定“菜条怎么写”，TLS 规定“匣子怎么做”。菜条写得再规矩，明着递还是会被看、被改、被冒充；匣子做得再好，也管不了店里给的鱼新不新鲜。这一篇只讲匣子；菜条的规矩在《明码点菜》。

TLS 在哪一层，管什么

TLS 位于应用层与传输层之间：上面是 HTTP、SMTP、IMAP 等应用协议，下面是 TCP（QUIC 则把 TLS 1.3 集成进传输层）。它不改变应用协议的报文格式，只在外面加一层“记录”（record）：应用数据被切成记录，加密、加认证标签，再交给 TCP 发送；收到后先验证、解密，再交给应用。TLS 提供三件事：机密性、完整性、身份认证。它不提供“应用可信”“数据在服务器上安全”“网站不是钓鱼站”这些保证。HTTPS 只是“HTTP over TLS”的简称；TLS 也可以保护其他协议。TLS 有记录层与握手层：握手负责协商版本、算法、密钥和身份，记录层负责之后每一段数据的加密与完整性。

握手：先验身份，再配钥匙

TLS 1.3 的完整握手大致是：客户端发 ClientHello，带上支持的版本、密码套件、SNI（要访问的域名）、密钥共享（key share）和随机数；服务器回 ServerHello，选定参数并给出自己的密钥共享；随后服务器发送 EncryptedExtensions、Certificate（证书链）、CertificateVerify（用证书私钥签名握手内容，证明自己真的持有私钥）和 Finished；客户端验证证书与签名、算出会话密钥，回 Finished。双方此后用会话密钥加密应用数据。TLS 1.3 通常 1-RTT；TLS 1.2 的完整握手通常 2-RTT。密钥交换常用 ECDHE：双方各生成临时密钥对，交换公开参数，各自算出同一个共享秘密，再经 HKDF 派生出握手密钥与会话密钥。这个过程的关键是：共享秘密从未在网络上传输；即使攻击者录下全部握手包，没有私钥也算不出来。每次连接都换临时密钥，就得到完美前向保密（PFS）。

证书与信任链：验印从哪来

服务器证书是 X.509 结构，里面写着域名（SAN）、公钥、有效期、用途、签发者，以及 CA 的签名。客户端拿到证书后，会沿证书链往上验：服务器证书由中间 CA 签，中间 CA 由根 CA 签，根 CA 的证书内置在操作系统或浏览器的信任库里。每一环都要验签名、有效期、用途和域名；根证书是信任锚，必须由系统预装或用户手动信任。CA 在签发前要验证申请者对域名有控制权（DV）、对组织有合法身份（OV/EV），但“有合法证书”不等于“是好人”：钓鱼站也能申请 DV 证书。证书透明度（CT）把签发记录公开，便于发现异常签发；CAA 记录限制哪些 CA 可以为某个域签发。吊销靠 CRL（证书吊销列表）与 OCSP（在线状态查询），OCSP Stapling 让服务器代查并附带结果；短期证书（如 90 天）则让失信的证书尽快自然过期。证书过期、域名不匹配、链不完整、系统时间错误，都会让浏览器报警。

加密与完整性：封条为什么不能伪造

TLS 记录层使用 AEAD（带关联数据的认证加密），常见算法是 AES-GCM 与 ChaCha20-Poly1305。AEAD 一次完成两件事：加密明文，并为密文与附加数据生成认证标签；接收方解密时先验证标签，标签不对就丢弃，不会把被篡改的数据交给应用。每条记录带序号，序号参与认证，重放或调换记录都会失败。对称加密之所以是主力，是因为它比非对称加密快几个数量级；非对称算法（ECDHE、RSA/ECDSA 签名）只用于握手阶段的密钥交换与身份认证。密钥由握手阶段的共享秘密经 HKDF 派生，分离出客户端写、服务器写、客户端读、服务器读等不同方向的密钥，避免复用。TLS 1.3 删掉了大量老旧算法（RSA 密钥交换、CBC 模式、RC4、压缩等），减少了降级与侧信道攻击面。

会话恢复、0-RTT 与版本差异

完整握手要一轮往返，移动网络下这一轮可能几百毫秒。TLS 支持会话恢复：服务器在第一次连接后发一个会话票据（session ticket），客户端下次带着票据来，双方用预共享密钥（PSK）跳过证书与密钥交换，省掉一轮。TLS 1.3 还支持 0-RTT：客户端在第一个飞行里就带上早期数据，代价是这些数据可能被重放，所以只适合幂等请求（如 GET），不适合“下单”“转账”。TLS 1.2 与 1.3 的差别不只是快：1.3 的完整握手使用临时密钥交换，默认具备前向保密；它还加密更多握手字段、简化密码套件、移除静态 RSA 与 CBC，安全性更好。配置上要关掉 TLS 1.0/1.1、弱套件与压缩，优先 1.3；但也要考虑老客户端兼容，必要时保留 1.2 的强套件。会话恢复与 0-RTT 都依赖票据密钥，票据密钥要定期轮换，否则长期泄露会削弱前向保密。

SNI、ECH 与“锁”的边界

握手时客户端要在 ClientHello 里告诉服务器“我要访问哪个域名”，服务器才能选对证书，这就是 SNI。SNI 在 TLS 1.3 里默认是明文的（除非用 ECH），所以同一网络里的人仍可能看到你访问了哪个域名——TLS 保护内容，不一定保护“你在访问谁”。ECH（Encrypted Client Hello）把 SNI 加密，减少这层泄露。另一个常见误会是地址栏的小锁：它只说明“这条连接加密了，证书与域名相符”，不说明网站可信、不说明服务器不会作恶、不说明你下载的文件安全。中间人如果能让客户端信任一张伪造的根证书（比如公司装的企业根证书、恶意软件装的根证书），TLS 仍然会被“合法”地解开；所以证书透明度、证书钉扎（pinning）、HSTS 等机制是在补这个缺口。TLS 还能做双向认证（mTLS）：客户端也出示证书，服务器据此认客户端；这在服务间调用、零信任架构里很常见。最后，TLS 常在反向代理或负载均衡处终止，代理之后到应用服务器这一段可能是明文或另一段 TLS；“端到端”到底到哪一端，要看架构。
