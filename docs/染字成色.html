染字成色

—— 一个关于“把话染成颜色”的故事

青溪县柳巷深处，有一家顾记染坊。顾师傅染了一辈子布，城里人拿一块旧布头来，他眯眼一看，便能调出一缸几乎一样的颜色。有人问他诀窍，他总说：“颜色不是一种东西，是一张配方。”

这一年，县衙旁的尺牍库换了新主事，姓陆。尺牍库里存着三十年的书信、契纸、状子和账册，堆了满满七间屋。陆先生想把这些旧纸按“说的是什么事”重新归拢：借粮的归借粮，修堤的归修堤，打官司的归打官司。

起初，他让书吏一页一页读，读完在纸上写一个签。可三十年的纸，读一年也读不完；更麻烦的是，同一件事，十个人有十种写法。有人写“借粮”，有人写“贷米”；有人写“河堤”，有人写“堤岸”；有人写“秋汛将至”，有人写“河水要涨”。书吏若只认字面，十封信里有八封会被分到不同的堆里。

陆先生为此愁了半个月。顾师傅来送染好的官布，听见他叹气，便问了一句。陆先生把难处说了，顾师傅想了想，说：“字我不懂，颜色我倒懂一点。你要找的是‘说的是同一件事’，不是‘写的是同一个字’，那能不能把每封信也染成一个颜色？”

陆先生只当他说笑。顾师傅却把徒弟阿砚叫来：“你替陆先生试一试。”

阿砚在染坊长大，知道师傅的配方从来不是一种染料。一缸颜色，要下靛、下黄、下红，还要看水的软硬、布的粗细、天气的干湿。同一种青，可能要多半勺靛，也可能要少半勺黄。颜色相近的两块布，配方也相近；颜色差得远的，配方也差得远。

阿砚想：既然颜色可以用一张配方来记，那“意思”能不能也用一张配方来记？

他在尺牍库里支了三百六十口小缸，每口缸里只放一种最基础的染料。每读一封信，他不在纸上写签，而是给这封信调一张配方：哪几口缸下多少，记成一长串数目。起初，配方是他随手定的，调出来的颜色乱七八糟：讲借粮的信和讲嫁娶的信，竟染成了同一种颜色。

陆先生摇头。阿砚便换了个法子。他请书吏把旧信里已经分好的堆指给他看：这一堆都是讲借粮的，那一堆都是讲修堤的；这一封和那一封虽说不是一件事，但都是讲田赋的，可以放得近些。阿砚照着这些旧堆，一缸一缸地改配方：同一堆里的信，尽量染得近；不同堆里的信，尽量染得远。改了一个月，又改了一个月。

到第三个月，配方渐渐稳了。陆先生拿一封新到的信来试。信上写的是“河堤失修，秋汛将至，请拨夫役”，通篇没有一个“堤岸”，也没有一个“护田”。阿砚把它染成一色，放进旧信堆里，旁边几封竟是十年前讲“堤岸坍塌，汛期护田”的呈文。陆先生翻了半天，叹道：“字不同，事倒是一件事。”

阿砚说：“颜色相近，只说明它们讲的事像。”

陆先生问：“像，不就是同一种事吗？”

阿砚摇头：“像，不等于对。”

没过多久，果然出了一桩错。库里有一封状子，写的是“算账”二字。阿砚把它染成一种颜色，归进了“钱粮纠纷”那一堆。可那状子讲的不是银钱，是两家人为了一句闲话，要“算账”出气。颜色相近，事却差得远。陆先生把状子抽出来，重新归了类。

又有一回，陆先生从邻县买来一张现成的“字色配方”。那配方在邻县用得极好，到了青溪县却不灵了：邻县人写“借粮”多用“贷米”，青溪县人却爱写“挪谷”；邻县靠山，青溪县靠水，同一句话里的味道也不一样。阿砚只好把三十年的旧信重新染了一遍。

顾师傅听说这些事，并不意外。他指着染坊里那三百六十口缸，对陆先生说：“配方能把颜色挪到一个可以比的地方，可不能替你判断这缸颜色该不该用。染坊只管染得像，穿出去体不体面，还得看裁缝和穿衣裳的人。”

陆先生把这句话记在尺牍库的门板上。后来，库里的信不再按“字”排，而是按“色”排；书吏找信，先看色，再读文。字还是那些字，只是从此多了一把可以量“像不像”的尺。

文本嵌入

Text Embedding · Embedding Model

这个故事讲的是文本嵌入（text embedding）：用一个模型把一段文字映射成一串数字，也就是一个向量。意思相近的文字，向量在空间里靠得近；意思差得远的，向量离得远。

故事里的“三百六十口缸”和“一张配方”，就是向量的许多维度；阿砚照着旧信堆反复调配方，就是模型从大量文本里学习参数；他给每封信染出的那一长串数目，就是这封信的 embedding。模型只负责“把话变成可比较的东西”，它不存储、不检索、也不替你判断真假。把这个向量拿去建索引、做检索，是后面〈问邻〉和〈一库三役〉的事；拿到检索结果组织回答，是〈先查后答〉的事。

什么是文本嵌入

文本嵌入是一类模型的能力：输入一段文字，输出一个固定长度的向量，例如 768 维、1024 维或 3072 维。向量的每一维本身没有人类可读的名字，它们共同构成一个“语义空间”。在这个空间里，讲“河堤失修”的句子和讲“堤岸坍塌”的句子，距离会比讲“婚嫁”的句子近得多。所谓“嵌入”（embedding），就是把离散的文字放进一个连续的数学空间里。

它为什么能表示语义

模型不是靠人手工写“近义词表”，而是从大量文本中学习。常见的训练方式有两类：一类是上下文预测，比如遮住一个词，让模型根据前后文猜；另一类是对比学习，把语义相近的句子作为正例、无关的句子作为负例，让正例的向量靠近、负例的向量远离。训练完成后，模型就学到了“哪些说法经常出现在相似的语境里”。这也是为什么它能处理“借粮”和“贷米”这种字面不同、意思相近的表达。

怎么比较两个向量

最常用的是余弦相似度（cosine similarity）：看两个向量的夹角，夹角越小越相似。它只关心方向，不关心长度，所以通常会先把向量归一化。也可以直接用点积或欧氏距离，但不同模型、不同训练目标适合的度量不完全一样。关键在于：建索引和查询必须使用同一种度量；否则分数没有可比性。

它不是搜索引擎

Embedding 模型只做“编码”。它不知道你的文档存在哪里，也不会自己去找近邻。真正把向量存起来、建索引、做 Top-K 检索的，是向量索引和向量数据库；把检索结果写成回答的，是大语言模型。把这三件事混成一件，是理解 RAG 时最常见的障碍。

工程上要记住的几件事

第一，模型有版本。换了模型或版本，旧向量和新查询向量往往不在同一个空间，必须重新索引。第二，模型有输入长度上限，超过部分会被截断，所以长文档要先切分。第三，模型有语言和领域偏好；一个在通用语料上训练的模型，到了医学、法律或古文语料上，效果可能明显下降。第四，模型有成本：在线 embedding 按 token 计费，批量索引时要把这笔账算进去。第五，模型不等于事实：两个向量相近，只说明它们“像”，不说明它们“对”。
