执

一封挂号信

—— 一个关于“丢了怎么办”的故事

汉口的同兴号票号，在京城、苏州、广州各设分号。商人在汉口交一笔银子，拿一张银票，到京城分号兑出现银——这是票号最要紧的生意。可早年的银票，只是一张写了数目的纸：交给镖师，镖师走一个月，路上丢了、抢了、泡了水，票号一概不认；收方说没收到，发方说早交了，两下里对不上，只能打官司。

同兴号的东家请了一位老账房。老账房在柜上坐了半辈子，见过太多“说不清”的账，来了之后，先立了一条规矩：从今往后，银票不叫银票，叫“挂号票”；不挂号，不出门。

挂号的头一件事，是“对号”。

汉口分号要往京城汇银，先不发票，先递一张“约票”过去：上头写着我方要开多少号、从几号起算。京城分号收到，回一张“约票”，上头写着我方也从几号起算，并把你那张约票的号抄回来。汉口再回一张“收到”。三张纸对完，两边才开始发票。

有伙计嫌麻烦：一来一回，半个月过去了。老账房说：不先对号，你发的票他那边不认，丢了也没处查；三张纸换的是往后几个月的明白。

对完号，每张票都编一个号：第一张是一号，第二张是二号，一直往下排；号不重复，也不跳。京城分号收到一张，就在回执上写一句“已收到第几号”；回执上写的不是“收到几张”，而是“连续收到第几号”——一号到十号都到了，就写“收到十号”；中间缺了七号，就写“收到六号，缺七号”，另在回执角上点一笔“缺七”。汉口一看，便知道七号丢了，补一张七号，再把后面的接着发。

挂号票最大的好处，是丢了能补；最大的坏处，是慢。

起初，汉口每发一张票，都要等京城的回执到了，才敢发下一张。一张票走十天，回执走十天，一个月只能发一张；商人们等不及，宁可多花银子找别家。老账房便改了法子：一次发一叠，不必等每一张的回执，只等“最前面那张”的回执。回执回来，窗口往前推一格，再补发一张。这样路上总有一叠票在走，又不至于发得没边。这一叠的大小，就叫“窗口”。

窗口大了，又出乱子。有一年秋天，京城分号柜上的现银不够，汉口不知情，照旧一叠一叠地发；京城收一张，兑不出银，只好把票压在柜上，回执也不发。汉口等不到回执，以为路上丢了，又重发一遍；越重发，京城压得越多，最后两家分号对着账本吵了三天。老账房这才在回执上添了一行：“本号现可再收若干张。”京城柜上现银少，就写“再收三张”；汉口照着这个数发，不敢多发。这便叫“收方的窗口”。

还有一桩，是路堵。那年官道上一支军队过境，车马挤了半个月。汉口不知路况，照旧发；票在道上越积越多，驿站收不下，丢的丢、压的压。老账房又立了一条：路上若连着丢票，发方自己先慢下来；先少发几张试试，若回执都回来了，再一张一张加上去；若又丢了，就减一半。他说：路是大家的路，你一个人把窗口开得再大，也快不过路；反倒是你慢一点，大家都快。

后来这一条写进了票号的规矩，叫作“见堵就退，见通就进”。

挂号票还有几样讲究。

一是乱序。票走的路不同，到京城的先后也不一定按号来：五号先到，三号后到，是常有的事。京城分号不按到的先后入账，先按号排好，缺号就等；等不到，才在回执上点名。这样账目不会因为路上颠倒了顺序而错。

二是重票。汉口重发七号的时候，原先那张七号可能并没有丢，只是走得慢；两张七号先后到了京城，京城只兑一张，另一张在角上盖“重”字，退回汉口。若不认号，两张都兑，票号就亏空了。

三是结清。两家分号把这一笔汇兑办完，不能一拍两散：汉口先发一张“结清票”，京城回执；京城再发一张“结清票”，汉口回执。四张纸走完，这笔账才算销了。销了之后，汉口还要把结清的底子留一会儿——怕最后一张回执在路上丢了，对方重发，自己却已经把底子烧了。留多久？老账房说，留到确定对方不会再问为止。

同兴号的柜台，也分了号。

一家分号里，有汇兑柜、存款柜、放款柜、兑票柜，各办各的事。挂号票上只写“京城分号”，到了分号门口，门房还得看票上写的“交某号柜”，才知道该往哪一张柜台送。若只写分号、不写柜台，票就在门房里堆着；堆久了，又成一本糊涂账。所以后来的挂号票，除了写分号的门牌，还要写柜台的号。

也有人寄“口信”——不挂号，不编号，托顺路的人捎一句“货已发出”。口信快，便宜，可丢了没人知道，重了也没人认。老账房说：口信有口信的用处，急事、短话、丢了也不打紧的，用口信；银子、契约、要留凭据的，必须挂号。两样不能混着用。

同兴号的墙上，后来挂了一块匾，四个字：有号有执。

TCP/IP

Transmission Control Protocol / Internet Protocol

这个故事讲的是 TCP，以及它和 IP 的分工。TCP/IP 其实是一套协议的名字，不是一个协议：IP 负责把一个个小包从源地址往目的地址送，只保证“尽力而为”；TCP 在两端把这条不可靠的通道，补成一条可靠、有序、有流量控制的字节流；UDP 则提供另一条更轻的路，不保证送达。故事里的票号是 TCP，门牌是 IP，柜台号是端口，口信是 UDP。上一篇《门牌与指路簿》讲地址与路由；这一篇讲地址之外，怎么让“丢了”变成“补得上”。

先把一个容易混的地方说清：TCP 传的不是“一封一封的信”，而是一串连续的字节。应用程序往里写多少字节，TCP 自己决定怎么切成段；收方看到的是一条按顺序排好的字节流，而不是一个个消息。所谓“信”的边界，要由应用协议自己划（比如 HTTP 的 Content-Length 或分块编码）。

TCP/IP 是一套，不是一个

“TCP/IP”是互联网协议族的统称，核心成员包括 IP、TCP、UDP、ICMP，以及支撑它们的 ARP、DNS 等。IP 在网络层负责寻址与转发，把数据装进包，尽力送到目的主机；TCP 和 UDP 在传输层负责把包分发给正确的进程，并各自决定要不要补可靠性。再往上，HTTP、DNS、SMTP 这些应用协议才真正理解“这串字节是什么意思”。这种分工像一只沙漏：上面有很多应用协议，下面有很多链路技术，中间只留 IP 一个窄腰。窄腰让任何新应用都能跑在任何新链路上，不必为每种组合重写一遍。TCP/IP 的名字来自两个最核心的协议，但它从来不是只有这两个。

柜台号：端口与套接字

IP 地址把包送到一台主机，端口把数据送到主机上的某个进程。端口是 16 位数，0 到 65535；0 到 1023 是知名端口（HTTP 80、HTTPS 443、DNS 53、SSH 22），1024 到 49151 是注册端口，再往上是临时端口。客户端发起连接时，操作系统随机分配一个临时端口；服务端监听固定端口。一个连接由四元组唯一确定：源 IP、源端口、目的 IP、目的端口。所以同一台服务器可以在 443 端口上同时服务成千上万个客户端，靠四元组区分。套接字（socket）就是这组地址与端口的编程抽象；NAT 改写的正是源地址与源端口，映射表也按四元组维护。端口不是“门牌”，同一个端口上跑什么服务由应用决定；把 80 当成“网站”只是约定，不是协议强制。

三次握手与四次挥手

TCP 是面向连接的。连接不是一条物理线，而是两端各自维护的一组状态：序列号、窗口、定时器、缓冲区。建立连接要三次握手：客户端发 SYN，带上自己的初始序列号；服务端回 SYN-ACK，带上自己的初始序列号并确认对方的；客户端再回 ACK。三次而不是两次，是为了让双方都确认“我能发、你能收”和“你能发、我能收”，并同步各自的初始序列号，避免旧连接的迟到包被当成新连接的数据。关闭连接通常要四次挥手：一方发 FIN 表示“我没有数据要发了”，另一方 ACK；等另一方也发完 FIN，再 ACK。主动关闭的一方进入 TIME_WAIT，等 2MSL，确保最后的 ACK 能到达，也让旧连接的残余包在网络里消散。半关闭、RST 强制重置、keep-alive 探测，都是这套状态机的边角。连接状态是有成本的：服务器要为每个连接保存缓冲区与状态，所以高并发服务会用连接池、事件驱动或 QUIC 来减少握手与状态开销。

可靠性是怎么补出来的

IP 只负责送，不负责送到。TCP 的可靠性靠四件事：编号、确认、重传、排序。发送方给字节流编号，接收方用累积 ACK 告诉它“这个号之前的都收到了”；发送方为未确认的数据启动定时器，超时就重发；收到三个重复 ACK，说明中间有一段丢了，立刻快速重传，不必等超时；接收方按序列号重排，把有序的字节交给应用，重复的段直接丢掉。SACK 让接收方可以点名“我还缺哪几段”，发送方只补缺口，不必把后面的全部重发。校验和能发现传输中的比特错误，但 CRC 更强的校验留给链路层；TCP 的校验和是端到端的兜底。要注意，TCP 保证的是“字节流可靠、有序”，不是“消息边界”：应用写两次，可能被合并成一个段；应用写一个大块，可能被切成很多段。消息边界要由应用协议自己定义。

窗口、流量控制与拥塞控制

发送方不能无限地发。两个窗口管着它：接收窗口（rwnd）是收方还能接收多少字节，防止把收方的缓冲区撑爆，这叫流量控制；拥塞窗口（cwnd）是发送方根据网络状况估计“路上还能放多少”，防止把网络压垮，这叫拥塞控制。实际发送窗口取两者较小值。拥塞控制通常从慢启动开始：cwnd 从小往大翻倍，直到出现丢包或达到阈值；然后进入拥塞避免，每个 RTT 加一点；丢包时把 cwnd 减半（AIMD 的乘法减小），再慢慢恢复。现代 Linux 默认常用 CUBIC，Google 的 BBR 则基于带宽与往返时延建模，不把丢包当成唯一信号。窗口大小还受带宽时延积（BDP）限制：链路越快、RTT 越长，路上能容纳的数据越多，窗口不够就会跑不满带宽。Nagle 算法与延迟 ACK 曾经常常互相等待，增加时延；现在很多低延迟场景会关掉 Nagle。缓冲区过大又会造成 bufferbloat：队列排得很长，吞吐不差，时延却高得难受。

UDP：另一条路

UDP 几乎只做两件事：加端口，算校验和。它不握手、不编号、不确认、不重传、不排序、不拥塞控制，所以开销小、时延低，但丢了就是丢了。它适合那些“迟到的数据不如没有”的场景：实时音视频、在线游戏、DNS 查询、DHCP、SNMP。应用如果要在 UDP 上做可靠传输，就得自己补序号、确认、重传、拥塞控制——QUIC 就是这么干的。QUIC 跑在 UDP 上，把可靠传输、加密、多路复用都放进用户态，解决了 TCP 的队头阻塞（一个连接里前面的包丢了，后面的数据即使到了也要等），还支持 0-RTT 恢复。HTTP/3 就是 HTTP over QUIC。TCP 与 UDP 没有高下，只有取舍：要可靠、有序、通用，选 TCP；要低时延、可容忍丢包、自己控制节奏，选 UDP。

TCP 不负责的事

TCP 不加密，不认证，不告诉你对方是不是真的那个网站——这些是 TLS 的事。TCP 不保留消息边界，不解释字节的含义——这些是应用协议的事。TCP 也不保证“快”：它保证可靠与公平，遇到丢包会减速；在弱网下，TCP 的保守可能让体验变差。TCP 还有队头阻塞：一个连接内，前一个字节没到，后面的字节不能交付给应用；HTTP/1.1 的管道化因此收益有限，HTTP/2 用多路复用缓解，但底层仍是同一个 TCP 连接，丢包时所有流一起等。理解这些边界，才不会把“用了 TCP”当成“问题都解决了”。可靠、安全、快速、低成本，是四件不同的事，分别由不同层负责。
