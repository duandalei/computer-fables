栈

认格不认人

—— 一个关于“生客也能取对货”的故事

汉口码头往上走半里，是同福栈。前院后院三百来格货架，茶叶、药材、布匹、杂货，一宗一宗分开放。每一格的门上钉一块木牌，牌上只写号，不写别的。

早年间不是这样的。

老掌柜在的时候，栈里没有号牌。客人站在柜前说一句“取三箱祁门红茶”，伙计应一声，自去后院搬。伙计认人，也认交情：张老板的茶靠东墙，李掌柜的药在里间第二架，王家的布压在最底下一格，压了三年，也没人来问。老掌柜记性极好，半个汉口，谁家的货在第几格，闭着眼都摸得到。二十年间，栈里没出过一次大错。

老掌柜一死，换了少掌柜。少掌柜是读书人出身，不认得几个货主。头一个月还撑得住——老伙计还在，照旧凭记性办事。到第二年，老伙计走了两个，新来的谁也不认得。祸就来了。

先是把李家的两箱茶，当王家的货发了出去。李家来讨，王家不认，两家在栈门口吵了三天，最后闹到县衙。接着又一桩：一个伙计记得里间第二架是陈货，把整格药材搬出去倒了；倒完才知道，那是济生堂刚进的一批川贝，值两百两银子。

少掌柜在柜后坐了三夜，算明白一件事：栈里的事，坏就坏在“认人”上。人走茶凉，记性会断，交情会错；三百格货，不能靠一个人的脑子管。

少掌柜把栈关了三天，重立栈规。

头一件是号牌。货在哪里，牌上就写哪里，别的一概不写。前院按货主分甲、乙、丙、丁，后院按货类分茶、药、布、杂，每一格再编一个数。丙字第七号，就是丙字第七号，从今日起不再改。牌上不许写“取货”“存货”“退货”——那些是客人要办的事，不是货。货只有一处，事可以有好几样，两样不能混在一块牌上。

一格里若有出入流水，也不往号牌上添字，另钉一块小牌：“丙字七号·出入”。

第二件是戳。

一张条子，先写号牌，再盖戳。戳只有五样：看、添、换、补、撤。

看，是看货；添，是往格里添新货；换，是把整格的货换成另一样；补，是只在货单上添一笔、减一笔，货不动；撤，是整格撤走。

这五枚戳，不分客人，不分伙计。江西来的客商，和汉口本地的老主顾，盖同一枚戳，意思一样；新上柜的伙计，和干了二十年的老伙计，看同一枚戳，办的事也一样。谁也不必认得谁。

少掌柜在柜上立了一块牌：认条，不认人。每张条子，都要随一份货主印或栈单。凭据不对，条子退回，货一箱不动；凭据对了，伙计照戳办，不必问来人是哪一位。一张条子只办一件事；写了两件的，退回去重写。

柜上原先只有一张桌。少掌柜又添了两张，三个伙计各接各的条子，办完各记各的簿。谁也不必知道旁人手上正办着什么，也不必等谁先办完。

头一天开张，来了个江西客商。他头一回到汉口，栈里没一个熟人。条子上写“丙字第七号”，盖的是“看”戳，随一张货主印。新上柜的伙计接过来，核对凭据，去后院看了格，回来抄了一张单子。

客商看着单子，忍不住问：你不问我是谁？

伙计说：条子上写着呢。

客商要开格看货。伙计摇头：格不能开。货开一次，潮气进去，下一位客人买的就是霉茶。客人要看，栈里抄一张货单：几时入的格、成色如何、斤两几何、存了多久。

抄单可以照客人的意思抄。写汉字的，抄汉字单；做洋庄生意的，抄洋码单。两种单子，写的是同一格货，斤两、成色一字不差。客人要哪种，伙计就抄哪种；没说的，照栈里的老格式抄。

也有客人不服：我出钱看货，怎么只给我一张纸？少掌柜说：你要的是货，货得留在格里；纸是货的样子，拿了纸，货跑不了。

回话也立了规矩。

客人问，办得怎么样？伙计只回固定的几句，不多说，不少说：“办妥了。”“新货入格了。”“无此号。”“凭据不符。”“条子写错。”“柜上出了事，稍候再来。”

有客人嫌这几句话冷。少掌柜说，回话若是看人下菜碟，规矩就没人信了。办成什么样，就回什么样；办不成的，也得回一句，不能让人站在柜前干等。

有一年梅雨，跑腿的伙计在雨里跑，听不见回话，怕条子丢了，便把同一条子递了两回。

“看”戳递两回，货单还是那张；“换”戳递两回，格子还是那格；“撤”戳递两回，第二回只见格子空着。都没出事。

“添”戳递两回，出了事：一箱变两箱，账上多出一箱无人认领的货。

少掌柜没法子，只好给“添”戳单立一条：凡盖“添”戳的条子，须在角上写一个号签，号签由柜上发，一号只入一回。同一号签再来，伙计翻号签簿，办过的，照原话回一句“办妥了”，货不再添。

后来这规矩也用到别处：办两回不出事的，不必写号签；会办出两回事的，非写不可。号签簿只留一个月，过了就烧——一个月的工夫，够一张条子跑完所有的来回了。

还有几桩小事，栈里也一并定了。

货挪了地方，号牌跟着货走，号不换。若一格实在要改名目，另立新号，旧号在簿上注明“已移至某号”。老主顾的条子还写着旧号，伙计照旧号一查，便知道新号在哪，不必让人空跑一趟。

栈门口的价牌，抄的人多。掌柜规定半个时辰换一回，牌底注着“某时抄”。过了时辰，抄本上的价不作数，自己回来重抄；没换过的，接着用。

日子一长，同福栈的名声传出了汉口。外埠的客商凭一张条子、一份凭据，就能在栈里办事，不必先来拜会掌柜，也不必打听今日是哪个伙计当值。

有外乡客商来栈里看，问少掌柜：一屋子生人进进出出，你连姓名都不问，不怕人把货搬空了？

少掌柜领他到院里，指着满墙号牌：

“货在哪个格，牌上写着；

要办什么事，戳上盖着；

来的是谁，凭据上印着。

三样齐了，我还问他姓名做什么？”

栈门口的石碑上，后来刻了一行字：认格不认人，认戳不认话。

谜底

REST 端点

REST · Resource Endpoint

这个故事讲的是 REST，以及“REST 端点”这个词所指的东西。REST 是 Representational State Transfer（表述性状态转移）的缩写，由 Roy Fielding 在 2000 年的博士论文里提出。它不是协议，也不是标准，而是一种组织网络接口的架构风格；它几乎总落在 HTTP 上，但也可以落在别的协议上。它由几条约束组成：资源用 URI 标识；对资源的操作靠一套统一的方法；客户端拿到的是资源的某种表述，而不是资源本身；每个请求自带全部信息，服务端不在两次请求之间记着你是谁；响应可以缓存；接口分层。故事里的号牌、五枚戳、认条不认人、抄单和固定回话，一样一样，都是这几条。

所谓“端点”（endpoint），就是一个 URI 加一个方法：对哪个东西，做什么事。同一个 URI 挂上不同的方法，就是不同的端点；不同的 URI 挂同一个方法，也是不同的端点。故事里的“丙字第七号 + 看”“丙字第七号 + 添”，就是两个端点。

每个资源有一个唯一、稳定的 URI；端点指向资源，而不是指向一次操作

格与号：资源、URI 与端点

REST 把世界看成一组资源（resource）。资源是任何可以被命名、被引用、被操作的东西：一张订单、一篇文章、一个用户、一批库存。每个资源有一个标识符，在 HTTP 里就是 URI。端点不是“文件的 URL”，而是“资源地址 + 方法”这一对——GET /orders/7 是读订单，DELETE /orders/7 是撤订单，路径不变，动作由方法承担。这就是故事里号牌只写格号、不写取货退货的道理：URI 标识的是“东西”，不是“要做的事”。路径里堆动词（/getOrder、/deleteOrder）的接口照样能用，但它把动词和名词混在一处，资源就失去了统一的名字，缓存、权限、文档都难做得整齐。资源也可以嵌套：/articles/12/comments 是文章下面的评论，对应“丙字七号·出入”那块小牌。层级不宜太深，一般两三层为止；深层路径往往可以用查询参数或单独的集合端点代替。

五枚戳：方法与语义

HTTP 的方法是一套事先约定好含义的动词。GET 取资源的表述，应当只读且有副作用为零；HEAD 与 GET 相同，只是不要正文，常用来探存在性与缓存。POST 提交数据，通常用于创建集合中的新成员，或者触发一个不太适合建模为资源修改的动作；它既不是安全的，也不保证幂等。PUT 用请求体整体替换目标资源，客户端自己指定 URI，所以 PUT 到不存在的地址可以创建资源（upsert）。PATCH 只做局部修改，语义由请求体的格式（如 JSON Merge Patch、JSON Patch）决定，一般来说既不是安全方法，也不保证幂等。DELETE 删除资源，重复删除通常仍返回成功或 404。安全（safe）与幂等（idempotent）是两件事：安全方法不改状态，幂等方法改一次和改多次结果相同。GET、HEAD、OPTIONS、TRACE 是安全的；GET、HEAD、PUT、DELETE、OPTIONS、TRACE 是幂等的；POST 与 PATCH 一般都不属于这两类。PUT 与 PATCH 的分工也常被混淆：整份资源交上去用 PUT，只交改动的那几个字段用 PATCH；但对并发写入，PATCH 需要配合 If-Match 与 ETag 才能防止覆盖别人的修改。

认条不认人：无状态

无状态是 REST 最硬的一条约束：服务端不在两次请求之间保留客户端的会话状态，每个请求都必须自带完成这次操作所需的全部信息——身份凭据、参数、版本、语言偏好。故事里柜上认条不认人，凭据随每条子一起递；三张柜台彼此不必通气，新伙计头一天也能办事。无状态的直接好处是可扩展：请求可以被任意一台实例处理，负载均衡不必做粘性会话；服务重启不丢会话；客户端重试安全得多。代价是每个请求都要重复携带凭据，通常用 Authorization 头里的令牌，或者签名过的 Cookie；令牌本身要能自证，或者能低成本地在服务端校验。要分清的是，“服务端不存会话”不等于“服务端不存数据”：订单、用户、库存当然存在数据库里，那叫资源状态，不叫会话状态。把登录态塞进服务端内存、靠 Cookie 找回，是很多“伪 REST”接口扩展不起来的根子——单机跑得好好的，一加机器就要粘性会话，一重启就全员掉线。

抄单：表述、协商与版本

客户端拿到的从来不是资源本身，而是资源在某一刻的表述（representation）。同一份资源可以有多种表述：JSON、XML、CSV、HTML，甚至同一媒体类型的不同字段集。客户端用 Accept 头说明自己能读什么，服务端用 Content-Type 说明自己给了什么；谈不拢就回 406。故事里汉字单与洋码单写的是同一格货，正是这个意思。JSON 是当下最通行的表述，但 REST 并不绑定 JSON。表述还牵出版本问题：接口一旦被人依赖，删字段、改类型、改路径都是破坏性变更。常见做法是把版本写进路径（/v1/orders/7）或媒体类型（application/vnd.shop.v2+json）；更稳妥的是只做加法、不改旧字段语义，把弃用期写清楚，给客户端留出迁移时间。再进一步是 HATEOAS：响应里带上下一步可用的链接，让客户端顺着链接走，而不是把路径硬编码在代码里——这正是 REST 原意里“超媒体作为应用状态引擎”的部分。绝大多数自称 REST 的接口只做到“HTTP + JSON + 资源化路径”，严格说只是 REST 风格，并非完整 REST；这不丢人，但要清楚自己省掉了什么。

回话：状态码与错误

状态码是接口的固定回话，客户端靠它决定下一步，而不是靠猜响应体的措辞。2xx 表示成功：200 带了正文，201 表示新建并应在 Location 头里给出新资源地址，204 表示成功但没有正文。3xx 表示资源在别处：301 永久移动、308 永久重定向且保持方法不变、307 临时重定向且保持方法不变、304 表示缓存仍然有效。4xx 是客户端的问题：400 请求格式有误，401 表示未认证（缺凭据或凭据无效），403 表示已认证但无权限，404 表示资源不存在，405 表示方法不允许（应带 Allow 头），409 表示状态冲突（如重复创建），422 表示格式正确但语义无法处理，429 表示限流。5xx 是服务端的问题：500 内部错误、502 上游网关出错、503 暂时不可用（可带 Retry-After）。故事里“凭据不符”与“无此号”必须分开回，正是因为客户端要据此做不同的事：前者去换凭据，后者别再重试。错误响应也应当有统一的结构，比如 RFC 9457 的 Problem Details（application/problem+json），带上类型、标题、状态码与说明，让客户端能程序化地处理，而不是解析一句人话。

重递：重试、幂等与缓存

网络会丢包，客户端会超时，代理会重发，用户会连点两下。REST 的对策是把“重复”当成常态来设计。GET、PUT、DELETE 天然幂等，重试最多多花一次往返；POST 不幂等，重试就可能多下一单、多添一箱货。业界通行的补救是幂等键：客户端为每次逻辑操作生成一个唯一键，放进 Idempotency-Key 头；服务端在首次处理时把键与结果一起记下，同一个键再来，直接重放上次的响应，不再执行业务。键要有一个合理的保留窗口（故事里的号签簿只留一个月），过期后允许复用；并发下同一个键同时到达，还要靠唯一索引或锁保证只有一次真正落库。缓存则是另一条减少重复的路：GET 响应可以标 Cache-Control（如 max-age=60、no-store），也可以带 ETag 或 Last-Modified；客户端下次带 If-None-Match 或 If-Modified-Since 来问，没变就回 304，连正文都不用传——门口价牌注明抄写时辰、过时重抄，说的正是这件事。写操作也可以用条件请求防并发：If-Match 不匹配就回 412，避免两个人同时改同一格货，后到的悄悄盖掉先到的。

五枚戳之外：REST 的边界

REST 擅长的是“对一组有名字的东西做增删改查”。转账、搜索、批量重算这类动作，硬塞进五个方法往往别扭；可以把它建模成资源（POST /transfers 创建一笔转账），也可以老实承认它是一个动作端点（POST /orders/7/cancel）。REST 不是唯一答案：gRPC 用接口定义语言和二进制协议，适合内部服务之间高频、强类型的调用；GraphQL 让客户端一次声明要哪些字段，适合前端需求多变、接口聚合多的场景；消息队列适合异步与解耦。选型看的是形状：资源清晰、读写为主、面向外部、需要缓存与通用工具链，REST 很合适；动作密集、延迟敏感、需要流式传输，别的风格可能更顺手。但无论用哪种，故事里的几条老规矩都成立：给东西起一个稳定的名字；用一套大家认得的动词；让每次请求自带全部信息；回话要有固定语义；把重复当成一定会发生的事。记住这些，比记住“REST 怎么写 URL”有用得多。
