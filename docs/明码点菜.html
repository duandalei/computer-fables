明码点菜

—— 一个关于“菜条人人都看得见”的故事

临江楼是府城里最大的酒楼。楼上楼下三十张桌，跑堂的伙计二十个，菜做得平常，生意却极好——因为它有一套极省事的点菜规矩。

客人进门，在柜上取一张菜条，照格式写：头一行写要什么，中间几行写几碗饭、几时上、要不要辣，末一行署名。写完搁在桌角的木托盘里。跑堂的看也不看人，只取菜条，冲后厨喊一声；后厨有菜，就在条子背面画个圈，没有便画个叉，忙不过来就写“候一候”。跑堂把条子送回桌上，客人照记号等菜。一顿饭吃完，条子收走，跑堂便再也不记得这位客人是谁——下一顿来，重新写。

这套规矩好在快。跑堂不必寒暄，不必记人，一张条子进来，一个记号出去，一天能翻三百桌。府城里的酒楼都学着这么办。

坏也坏在这张条子，是明写的。

对门有家黑店，专门在大堂里做手脚。客人写“清蒸鲥鱼”，跑堂转身的工夫，条子被人抽走，换上一张“臭鳜鱼”；客人写“二两银子的席面”，半路被添了一笔，成了“二十两”。更狠的是，有人在门口摆了张桌子，穿一身和临江楼一模一样的短褂，见人就伸手接菜条，接了便跑——客人还当他是跑堂，等到日头偏西，菜也没来。

掌柜的报了官。官差来了，看看大堂，摇头：条子摆在托盘里，谁都能伸手；跑堂只认条子，不认人。这案子，没法查。

掌柜的先试过别的法子：把菜条的字写小，把菜名换成暗语，在托盘上盖一块布。黑店的人跟着学，不出三日，暗语也会了，布也掀了。掌柜的这才明白：菜条从客人的手到后厨，要过好几道手；只要它还是明着从大堂上过，换什么写法都没用。

掌柜的又在柜台后坐了三天。这回他想明白了两件事：菜条本身的规矩没有错——一张条子写清要什么、几时上、送到哪一桌，跑堂不必认人，后厨不必记客，一天翻三百桌，全靠这套格式；错的是这张条子明着从大堂上过。

可要封住它，不是改菜条的写法。写成暗语，黑店三天就学会；把字写小，换张布盖上，也不过是遮眼。菜条的格式得原样留着，另做一只匣子，把整张条子封进去。

掌柜的便请了一位做匣子的老师傅。临江楼的菜条还是那张菜条，只是递法要变了——匣子的事，另有一则故事。

谜底

HTTP

HyperText Transfer Protocol

这个故事讲的是 HTTP（HyperText Transfer Protocol，超文本传输协议）：万维网上客户端与服务器一问一答的格式。它规定了请求怎么开头、头部怎么写、状态码怎么回、正文装什么；它不规定正文里的 HTML、JSON、图片长什么样。故事里的菜条，就是 HTTP 报文：头一行写要什么（方法 + 路径），中间几行写要求（头部），末一行署名（凭据）；跑堂画的圈、叉、“候一候”，就是状态码。

HTTP 本身不负责保密、完整性和身份认证：菜条明着从大堂上过，谁都能看、能改、能冒充。要解决这三件事，得在 HTTP 外面套一层 TLS，也就是 HTTPS；那是《封匣》的事。这一篇只讲菜条的写法与递法。

报文长什么样

一次 HTTP 对话只有两步：客户端发一个请求，服务器回一个响应。请求的开头是请求行——方法、路径、协议版本，例如 GET /menu HTTP/1.1；接着是头部，说明要什么格式、来自哪个站点、带了哪块熟客牌子；最后是可选的正文。响应也是三段：状态行（如 HTTP/1.1 200 OK）、响应头、响应正文。HTTP/1.1 的报文是文本，头部一行一个字段，空行之后是正文；HTTP/2 与 HTTP/3 改成了二进制帧，但方法、状态码、头部的语义不变。头部里常见的字段：Host 指定站点，Accept 说明能接收什么类型，Content-Type 说明正文是什么类型，Content-Length 或 Transfer-Encoding: chunked 说明正文有多长，Cookie 带凭据，Cache-Control 管缓存。HTTP 只管格式与语义，不规定正文里装什么——HTML、JSON、图片、视频都装得下，这就是“超文本”后来能承载整个万维网的原因。

方法与状态码

方法是动词：GET 取资源，HEAD 只要头部，POST 提交数据或触发动作，PUT 整体替换，PATCH 局部修改，DELETE 删除，OPTIONS 探能力。GET/HEAD/OPTIONS 是安全方法（不改状态），GET/HEAD/PUT/DELETE/OPTIONS 是幂等方法（重复执行效果相同）；POST 与 PATCH 一般不保证幂等。状态码是回话的固定语义：2xx 成功（200 OK、201 Created、204 No Content），3xx 重定向（301 永久、302 临时、304 未修改、307/308 保持方法），4xx 客户端问题（400 格式错、401 未认证、403 无权限、404 不存在、405 方法不允许、409 冲突、422 语义错、429 限流），5xx 服务端问题（500 内部错误、502 上游错误、503 暂时不可用、504 上游超时）。状态码要选准，客户端才能程序化地决定重试、跳转还是报错；把错误都包成 200 再在正文里写“失败”，会让缓存、监控、重试都失去依据。

无状态、Cookie 与 Session

HTTP 是无状态的：每个请求自带足够的信息，服务器不必记得上一个请求是谁发的。好处是简单、易扩展：任何一台服务器都能接住下一个请求，坏了换一台也不丢状态。麻烦是“登录”无处安放。于是有了 Cookie——服务器在响应里塞一张小纸条（Set-Cookie），浏览器此后每次请求自动附上；常见做法是纸条上只写一个编号，真正的登录记录仍存在服务器的 Session 里，或者把身份信息签名后放进令牌（如 JWT），让服务端不必存 Session。Cookie 的安全属性要配好：HttpOnly 防脚本读取，Secure 只走 HTTPS，SameSite 降低 CSRF 风险，Max-Age/Expires 控制有效期。无状态不等于“完全不存数据”：用户、订单、库存当然要存数据库；不存的是“这次对话的上下文”。把两者混为一谈，就会把 Session 塞进单机内存，最后被粘性会话和重启掉线拖住。

代理、缓存与连接

HTTP 的中间可以站很多角色：正向代理替客户端转发，反向代理替服务器接客，CDN 把内容放到离用户近的边缘，负载均衡把请求分给多台后端。缓存是 HTTP 性能的关键：Cache-Control 说明能缓存多久、谁能缓存，ETag/Last-Modified 让客户端下次带 If-None-Match/If-Modified-Since 来问，没变就回 304，连正文都不用传。连接方面，HTTP/1.1 默认 keep-alive，复用同一条 TCP 连接，但同一连接上的请求仍有队头阻塞；HTTP/2 在一条连接上多路复用多个流、压缩头部，但底层 TCP 丢包仍会让所有流一起等；HTTP/3 把可靠传输搬到 QUIC（跑在 UDP 上），每个流独立重传，解决了 TCP 层的队头阻塞。版本越高并不自动越快，还要看网络、服务端和缓存策略。

HTTP 不负责安全

HTTP 是明文协议：路径、查询串、头部、Cookie、正文都可能被同一网络中的中间人看见；它也不提供完整性保护，半路可以改请求或响应；它更不验证对方身份，客户端无法仅凭 HTTP 确认对面真是目标服务器。把菜条写小、换暗语、盖块布，都只是编码或混淆，不是加密。要补这三件事，得在 HTTP 与 TCP 之间加一层 TLS：HTTPS 就是 HTTP over TLS，报文格式一字不改，整段对话先加密、再认证。TLS 的握手、证书、密钥交换、吊销与边界，见《封匣》。记住：HTTPS 保护的是“传输中”，不保护服务器内部的数据，也不保证网站是好人；钓鱼站同样可以申请合法证书。

HTTP 与 REST 不是一回事

HTTP 是协议，规定报文怎么发、方法是什么意思；REST 是一种架构风格，主张用 URI 标识资源、用统一的方法操作资源、无状态、可缓存。一个接口用了 HTTP，不等于它就是 REST；一个 REST 接口也不一定非用 HTTP。故事里的菜条是 HTTP 的报文格式；至于菜谱怎么组织、哪道菜对应哪个资源、端点该叫 /dishes/7 还是 /getDish?id=7，那是《认格不认人》里的事。把协议和风格分开，才不会把“用了 GET/POST”当成“设计好了 API”。
