库

一库三役

—— 一个关于“谁存、谁找、谁染色”的故事

青溪县下游的码头边，有一座聚源绸缎库。库里存着从苏杭运来的绸、缎、纱、绢，一匹一匹卷在木架上，按年份、产地、客商分间存放。钱掌柜管着这座库，最得意的是库里的“三役”：仓管老赵、册房先生周先生、染匠顾师傅。

老赵管货。哪一匹布在哪一排哪一架，什么年份进的，什么成色，哪家客商订的，他都写在货签上，系在布头。周先生管簿。库里的每一匹布，他都让顾师傅染一张色卡；再把色卡按颜色远近编成一本邻里簿。顾师傅管色。客人拿一块样布来，他调出配方，染出一张新色卡。

客人来买布，先到顾师傅那里染样色；周先生拿样色去邻里簿上找几张相近的色卡；老赵按色卡上的编号去架上取布；客人再在取来的几匹里挑。三个人各做一段，合起来才是一桩买卖。

日子久了，钱掌柜却起了别的心思。他看周先生每天只是在簿子上写写画画，既不下架，也不搬布，便觉得这册房先生是白吃干饭的。他问老赵：“库里的布，你闭着眼也找得到吧？”老赵说：“找得到是找得到，可库里十万匹布，一匹一匹翻，客人等不起。”钱掌柜不听，年底把周先生辞了。

开春第一桩大买卖就出了事。一位外地客商要一批“雨过天青”的素缎，钱掌柜让老赵去库里找。老赵从第一排找到最后一排，搬了三百多匹，颜色不是深了就是浅了；客人等了半日，甩袖走了。钱掌柜又让顾师傅去找，顾师傅能染，却记不住十万匹布放在哪。库房还是那座库房，布也还是那些布，可没有那本邻里簿，谁也不知道“最像的那几匹”在哪。

钱掌柜只好把周先生请回来。周先生没说什么，只把邻里簿重新摊开，又添了一条规矩：来查布的人，不只要说颜色，还要说清“哪一年的”“哪家客商的”“要不要带暗花的”。老赵的货签上本来就有这些字，周先生便把它们抄在色卡旁边。客人若只要“今年、李家、素缎”，簿子便先把别的年份、别家客商、带暗花的色卡拨到一边，再从剩下的里面找颜色最近的。

钱掌柜看得稀奇：“原来这簿子不只是记颜色。”

周先生说：“颜色管‘像不像’，货签管‘是不是’。”

又过了两年，库里出了一场小火。火从册房起，烧了半屋子簿子。钱掌柜急得直跺脚，周先生却先去看货架：“布还在，货签还在，就能重编。”他带着阿砚，照着货签上的年份、产地、客商，再让顾师傅重新染一遍色卡，花了两个月，把邻里簿重新建了起来。

钱掌柜这才明白：布是根，簿是影。布没了，簿子记得再清楚也没用；簿子没了，布还在，可以照布重编。

可事情还没完。有一年夏天，江水涨上来，淹了半座库房。水退之后，布匹霉的霉、烂的烂；邻里簿倒还在，一页没湿。钱掌柜翻着簿子叹气：“这簿子倒比布还结实。”周先生摇头：“簿子结实有什么用？它记的那些布，已经没了。”

钱掌柜这才把三役的分寸刻在库门上：仓管管“有什么”，册房管“怎么找”，染匠管“怎么比”。三者缺一，买卖就做不成；可三者也不能混着叫。

后来有年轻的伙计问周先生：“您这册房，和库房到底是不是一回事？”

周先生指着库房和簿子，说了一句：

“库是库，簿是簿，管家是管家。

有时候一个人兼了三样，也不能把三件事说成一件事。”

谜底

向量数据库与索引引擎

Vector Database · Index Engine

这个故事讲的是向量数据库（vector database）、索引引擎（index engine）、向量索引（vector index）和embedding 模型之间的关系。它们经常被混着叫，其实各管一段：模型负责“把文本变成向量”，向量索引负责“把向量排成能快速找近邻的结构”，索引引擎负责“建索引、维护索引、查索引”，向量数据库负责“把向量、原文、metadata 存起来，并做持久化与增删改查”。

在〈染字成色〉里，顾师傅是 embedding 模型；在〈问邻〉里，邻里簿是向量索引；在这一篇里，周先生是索引引擎，整座聚源库是向量数据库。现实中的 Chroma 往往一人兼了“库”和“管家”两役，但它内部仍然分得清：collection 是仓库，HNSW 是簿子，查询接口是管家。模型不在 Chroma 里面——在这个项目里，是应用层先算好向量，再交给 Chroma。

metadata：用于过滤、溯源、展示的附加字段
按客商、年份分间存放
collection / namespace：逻辑隔离，避免不同用户或不同空间混查

四个词，不是四样并列的东西

Embedding 模型是模型，负责编码；向量索引是数据结构，负责近邻查找；索引引擎是软件组件，负责建、维护、查索引；向量数据库是系统，负责存储、持久化、metadata、过滤和增删改查。很多产品会把“索引引擎”和“向量数据库”做在一起，所以日常会把它们混着叫；但排错时一定要分开：是模型编码不对，是索引召回不够，还是存储/过滤条件写错了。

向量数据库到底多做了什么

如果只是“存一堆向量、查最近邻”，一个内存数组加暴力比较也能做到。向量数据库多出来的是工程能力：持久化到磁盘、进程重启后还在；按 id 增删改查；存原文和 metadata；按字段过滤；分 collection 做隔离；并发访问；备份与恢复；有的还支持多副本、分片和权限。故事里“按年份、客商分间存放”和“货签上的字”，就是 collection 与 metadata 的类比。

索引引擎和索引有什么区别

索引是“簿子”，索引引擎是“编簿、查簿、补簿的人”。HNSW 是索引结构；Chroma 里的 collection 管理和查询执行，是索引引擎的职责。你可以换一种索引结构（HNSW 换 IVF），也可以换一个索引引擎（Chroma 换 FAISS 或 Milvus），这两件事的影响不同：换结构主要影响召回、延迟、内存；换引擎还会影响持久化、过滤、部署和 API。

Chroma 在这个项目里是什么

项目把 Chroma 当作一个嵌入式向量数据库用：PersistentClient 指向本地 data/chroma，每个用户一个 collection（在线空间是 kb_user_{user_id}，本地兜底空间是 kb_user_{user_id}_local），建 collection 时指定 hnsw:space=cosine。写入时调用 collection.upsert(ids=..., embeddings=..., documents=..., metadatas=...)，查询时调用 collection.query(query_embeddings=...)。注意：向量是应用层用 embedding 模型算好后传进去的，不是 Chroma 自己调的；在这个项目里，模型和索引引擎的边界非常清楚。

索引是派生数据

故事里“册房失火，照货签重编”，说的就是索引可以从源数据重建。项目里真正的事实来源是上传的原件和 SQLite 里的分块记录；Chroma 里的向量索引是可以重建的。项目用确定性 id item{item_id}_chunk{chunk_index}，重索引时覆盖旧向量，删除文档时按 item_id 清理。即使向量写入成功、关系库写入失败，留下“幽灵向量”，重新索引或删除也能收敛。这也是为什么流水线敢“先写向量库，再写关系库”：索引坏了可以重建，源数据不能丢。

选型与边界

Chroma 适合单机、小到中等规模、想少运维的场景；它的优势是嵌入应用、开箱即用，不需要单独起服务。规模再大、并发再高、要多副本多租户时，才需要考虑 Milvus、Qdrant、Weaviate 这类独立服务。无论用哪种，问题都还是那几类：模型是否匹配、维度是否一致、距离度量是否统一、索引参数是否合适、metadata 过滤是否正确、索引是否该重建。把这些分开看，选型和排错都会清楚很多。
