先查后答

—— 一个关于“先翻档案，再开口”的故事

青溪县衙里，沈先生做了二十年的师爷。他读过书，记性好，方大人问起旧事，他多半能接上话；接不上时，他也不肯说“不知道”，总要顺口编一个像模像样的说法。

有一年春天，方大人问：“西村去年借出去多少粮？”沈先生略一沉吟，答：“三百石。”方大人又问：“账上呢？”差役去尺牍库翻了半日，回来禀报：“二百石，另有二十石是借给东村的。”堂上静了片刻。

方大人问：“你记得三百石，是记错了，还是编的？”

沈先生低着头：“我记得从前有一桩相似的案子，也是三百石。”

方大人说：“相似，不是同一件。”

从那天起，县衙立了一条新规矩：凡是问事实，沈先生开口之前，必须先让差役阿福去尺牍库查档；查回来的卷宗，他要先读，再答。答的时候要写明“据某年某卷”；若库里没有，就说“库里没有”，不许拿“我记得”来顶；若库里说的和他记得的不一样，以库里为准；若要补充自己的见识，也要明说“这是据常理推断”，不能混进档案里。

阿福起初不乐意，觉得这规矩慢。可他有周先生编的邻里簿，查档并不慢：先把方大人的问题写成一张“问题条”，拿去库里按意思找几张相近的卷宗，再按年份、村落、事由筛一遍，挑出三五卷，抱回来。沈先生读完，才开口。

头一回试新规矩，问的正是西村借粮。阿福抱回三卷：一卷是西村借粮二百石的呈文，一卷是东村借粮二十石的附册，还有一卷是前年西村还粮的收据。沈先生逐卷读完，答：“据某年某卷，西村借粮二百石；东村另有二十石，不在西村账内；前年已还一百五十石，余五十石未清。”方大人点点头：“这回有出处。”

第二回却碰上一件麻烦事。方大人问“河工银两”，阿福抱回七八卷，有修堤的，有挖渠的，有买木料的，还有一卷是河神庙的香火账。沈先生读了一遍，只留下三卷与“河工银两”直接相关的，其余放在一边。方大人问：“那几卷呢？”沈先生说：“不相干。凑进来，反倒把正事搅浑了。”方大人又问：“你怎么知道不相干？”沈先生说：“我先看它讲的是不是同一件事，再看它有没有我要的数。像，不等于就是。”

第三回，方大人问起一条刚颁下的新例。阿福去库里翻了半天，回来说没有。沈先生便答：“库里没有这条新例。以下是我按旧例和朝廷律令推的，未必作准，请大人再核。”方大人看了他一眼，没说什么，只让他把“未必作准”四个字写在条陈上。

第四回，一个老农来问孩子发热该怎么办。沈先生让阿福去库里找，库里只有田赋、水利、婚约，没有医书。沈先生便说：“库里没有医案。按常理，先请郎中；若高热不退，莫耽搁。”他没有把“常理”说成“档案”，也没有装模作样地开方子。

第五回，方大人只是随口问了一句“今日天色如何”。沈先生没有让阿福去查档，抬头看了看天，答了。方大人笑：“这回怎么不查了？”沈先生说：“这不是档案里的事。该查的查，不该查的不查；查得太多，也是耽误工夫。”

日子一长，县衙里的人发现，沈先生的回答慢了一点，却稳了很多。从前他答得快，数字常常要再核；如今他答得慢，卷宗号、年份、数目都在纸上，谁都能去对。方大人问他：“你这套法子，究竟靠的是哪一样？是阿福会跑，是周先生的簿子，还是你自己会写？”

沈先生想了想，说：“都靠，也都不是单靠一样。

阿福会跑，可他要是不认得路，抱回来的就是一堆废纸；周先生的簿子编得再细，可库里要是没有那几卷，也找不出东西；我会写，可我要是先开口再查，写出来的还是编的。

先查，后答；查得到的，说得出出处；查不到的，说得出‘没有’。这三件事合起来，才叫一个‘答’字。”

谜底

检索增强生成

RAG · Retrieval-Augmented Generation

这个故事讲的是检索增强生成（RAG，Retrieval-Augmented Generation）：在让大语言模型回答之前，先从外部知识库里检索相关内容，再把“问题 + 检索到的片段”一起交给模型，让它据此作答，并尽量标明来源。

故事里，沈先生是生成答案的模型，阿福是检索器，尺牍库是外部知识库，问题条是查询，周先生的邻里簿是索引。〈染字成色〉、〈问邻〉、〈一库三役〉讲的是“怎么把知识找出来”；这一篇讲的是“找出来之后，怎么答”。RAG 的核心不是某一个组件，而是先检索、再生成、答必有据这条完整的链。

沈先生
大语言模型（LLM）：负责理解问题、组织语言、生成回答
差役阿福
检索器（retriever）：负责把问题送到知识库并取回候选
尺牍库
外部知识库：文档、笔记、数据库、网页等，模型训练时没见过
问题条
查询（query）：用户问题，必要时会被改写或拆解
周先生的邻里簿
索引：向量索引、关键词索引或混合索引
抱回三五卷
Top-K 片段：检索返回的候选 chunk
只读这几卷再答
把检索结果放进上下文，再让模型生成
写明“据某年某卷”
引用与溯源：让答案可以被核对
库里没有就说没有
无答案识别（no-answer）：不把“没找到”编成“找到”
档案与记忆冲突，以档案为准
来源优先级：检索到的事实优先于模型记忆
自己的见识要标“据常理推断”
区分检索内容与模型自带知识，避免冒充来源
卷宗残缺、过期
数据质量与时效性：RAG 的上限由知识库决定
阿福抱回不相干的卷
检索误差：召回不准会污染上下文
问题太宽，先拆成几问
查询改写、查询拆解、多路检索
卷宗太多读不完
上下文预算：Top-K、去重、重排、截断
闲聊不必查档
意图路由：不是所有问题都要走检索
只问不查
纯 LLM 问答：容易幻觉，知识停留在训练数据
只查不答
纯检索：返回片段，不生成自然语言答案

RAG 是什么，不是什么

RAG 是一种架构，不是某个模型，也不是某个数据库。它的最小形态是“检索 + 生成”：先用问题去外部知识里找相关内容，再把内容放进 Prompt 让模型回答。它不改变模型的参数，所以和微调（fine-tuning）不是一回事；它也不等于“联网搜索”，知识库可以是本地文档、数据库、维基、工单，当然也可以是网页。

三个环节：索引、检索、生成

索引：把文档解析、切分、编码成向量或关键词索引，存进知识库。检索：把问题编码，去索引里找 Top-K，按阈值过滤，必要时重排。生成：把问题与检索片段组装成 Prompt，让模型作答，并要求引用来源、无据时说无据。故事里“编簿、查档、写条陈”，正好对应这三段。

那四个词在 RAG 里是什么位置

Embedding 模型、向量索引、向量数据库、索引引擎，主要覆盖“索引”和“检索”这两段，是向量检索的底座，不是 RAG 的全部。RAG 还缺不了文档解析与切分、查询改写、Top-K 与阈值、Prompt 模板、LLM、引用与无答案策略、评估与观测、以及把这一切串起来的编排。只把四个词背下来，仍然搭不出一个可靠的 RAG。

RAG 不一定需要向量数据库

检索可以是关键词检索（BM25、SQLite FTS5、Elasticsearch），可以是向量检索，也可以两路混合；可以没有独立的向量数据库，用 FAISS 甚至一个内存数组也能做；可以用知识图谱、SQL 查询、网页搜索。RAG 的核心是“先取外部知识，再生成”，不是“必须用 Chroma”。选哪种检索，取决于数据形态、查询类型、延迟和运维成本。

决定 RAG 好不好用的，往往不是模型

切分是否保留了上下文？embedding 是否适合这个领域？Top-K 取多取少？阈值定得高不高？检索结果有没有重排？Prompt 有没有要求“只依据片段回答”？无答案时会不会硬编？答案有没有来源？这些问题，往往比“换一个更大的模型”更影响体感。故事里沈先生答得准，不是因为他更聪明，而是因为阿福抱回的卷宗对、他只读对的卷、并且敢说“库里没有”。

这个项目里的 RAG

项目把知识库限定为个人库：上传 PDF/DOCX/PPTX/MD/TXT，解析、切分、embedding，写进 Chroma；提问时用 embedding 模型把问题编码，去同一个向量空间检索 Top-K，按 RAG_MIN_SCORE=0.55 过滤，再按“有据 / 无据 / 闲聊”三套模板组装 Prompt，交给 LLM 生成。Agent 的 search_knowledge_base 工具复用的也是这条链路；检索结果会以 sources 事件推给前端，来源卡片可以跳回原文。这里没有联网搜索，也没有跨用户的知识库——这正是“先查后答”里“查得到什么、查不到什么”的边界。
