明码点菜

—— 一个关于“菜条人人都看得见”的故事

临江楼是府城里最大的酒楼。楼上楼下三十张桌，跑堂的伙计二十个，菜做得平常，生意却极好——因为它有一套极省事的点菜规矩。

客人进门，在柜上取一张菜条，照格式写：头一行写要什么，中间几行写几碗饭、几时上、要不要辣，末一行署名。写完搁在桌角的木托盘里。跑堂的看也不看人，只取菜条，冲后厨喊一声；后厨有菜，就在条子背面画个圈，没有便画个叉，忙不过来就写“候一候”。跑堂把条子送回桌上，客人照记号等菜。一顿饭吃完，条子收走，跑堂便再也不记得这位客人是谁——下一顿来，重新写。

这套规矩好在快。跑堂不必寒暄，不必记人，一张条子进来，一个记号出去，一天能翻三百桌。府城里的酒楼都学着这么办。

坏也坏在这张条子，是明写的。

对门有家黑店，专门在大堂里做手脚。客人写“清蒸鲥鱼”，跑堂转身的工夫，条子被人抽走，换上一张“臭鳜鱼”；客人写“二两银子的席面”，半路被添了一笔，成了“二十两”。更狠的是，有人在门口摆了张桌子，穿一身和临江楼一模一样的短褂，见人就伸手接菜条，接了便跑——客人还当他是跑堂，等到日头偏西，菜也没来。

掌柜的报了官。官差来了，看看大堂，摇头：条子摆在托盘里，谁都能伸手；跑堂只认条子，不认人。这案子，没法查。

掌柜的先试过别的法子：把菜条的字写小，把菜名换成暗语，在托盘上盖一块布。黑店的人跟着学，不出三日，暗语也会了，布也掀了。掌柜的这才明白：菜条从客人的手到后厨，要过好几道手；只要它还是明着从大堂上过，换什么写法都没用。

掌柜的在柜台后坐了三天，想出一个法子。他把客人请到堂前，说：

“菜条不能明着递了。从今日起，临江楼备一只匣子。

菜条封进匣里，大堂上谁也看不见、改不了。

可客人得先认准：这匣子真是临江楼的。”

每只匣底，都刻着本楼的字号。字号由商会作保——府城里任何一家字号，都能到商会领一枚作保的印样；客人拿匣底的字号与商会挂出的印样一对，是真是假，一看便知。

接下来是对钥匙。客人先把自己的锁锁在匣上，送到柜上；柜上打不开，便再加上自己的一把锁，原样送回；客人开自己的锁，再送回去；柜上开自己的锁。一来一回，匣里留下一把只有这两把锁配得出的临时钥匙。此后不论传多少张菜条，都用这把钥匙开匣关匣。

黑店的人再来，抽走匣子，打不开；半路换一只匣子，匣底字号对不上，客人当场就不点了；冒充跑堂在门口接匣子的，客人先问一句“匣底字号”，他答不上来。

一顿饭吃完，临时钥匙当场作废。下一顿来，重新对一次锁，配一把新的。

可封了匣，也不是万事大吉。

有客人问：匣子封着，是不是就说明这家店童叟无欺？

掌柜的摇头：匣子只保三件事——菜条没被人偷看，没被人改动，对面接匣子的确是临江楼。至于临江楼给的鱼新不新鲜、账算得对不对，匣子管不着。

又有客人问：那要是临江楼自己把钥匙给了别人呢？

掌柜的说：所以字号印要由商会作保。商会查实一家，才给一枚印样；哪天查出临江楼私配匣子、把客人的菜条往外递，商会当场摘了它的字号。客人每日在门口对一对印样，就知道今天还能不能在这儿吃。

后来府城的酒楼都换上了封匣。大堂里再没有一张明写的菜条，跑堂还是不必认人，客人还是不必寒暄，一桌菜照样上得飞快。

有外乡人不解，问掌柜：从前菜条明着递，也吃了十几年，何苦费这些事？

掌柜的把一只封好的匣子摆在柜上：

“从前是大堂里人人都长着眼睛，只是没人说破。

菜条还是那张菜条，规矩还是那套规矩；

多的只是一只匣子——让该看的人看得见，不该看的人看不见。”

HTTP 与 HTTPS

HyperText Transfer Protocol · HTTP over TLS

这个故事讲的是万维网上最基本的一问一答：HTTP（HyperText Transfer Protocol，超文本传输协议），以及把它整段封进匣子的 HTTPS。HTTP 规定了客户端与服务器“怎么说话”——请求行、头部、正文，一个请求配一个响应；它不负责保密，也不负责证明对方是谁。HTTPS 没有改动这套说法，只是在 HTTP 与底层网络之间加了一层 TLS：先验明对方身份，再协商出一把只有双方知道的钥匙，把整段对话封起来。

菜条头一行写要什么，中间几行写要求，末一行署名
HTTP 报文结构：请求行（方法 + 路径 + 版本）、头部、正文
跑堂画圈、画叉，忙不过来写“候一候”
状态码：2xx 有菜、4xx 条子写得不对、5xx 后厨出了事
跑堂不认人、不记事，下一顿重新写
HTTP 无状态（stateless）：每个请求彼此独立，服务器不保存上一回的上下文
熟客的牌子，跑堂才记得他上一回点了什么
Cookie 与 Session：在无状态协议上补一层记忆
菜条明写，大堂里谁都能看
HTTP 明文传输：路径、头部、正文都可被同一网络中的中间人读取
半路把鲥鱼换成臭鳜鱼，二两改成二十两
中间人篡改（MITM tampering）：HTTP 不提供完整性保护
穿短褂冒充跑堂，在门口接菜条
冒充服务器与钓鱼攻击：HTTP 不验证对方身份
换小字、换暗语、在托盘上盖布
自定义编码与混淆不是加密：改写法挡不住能读的人
封匣传菜
HTTPS：HTTP over TLS，在应用层协议之下加密整条通道
客人上锁、店里加锁、各自开锁，匣里留下一把临时钥匙
TLS 握手：以 ECDHE 等算法交换密钥，协商出对称会话密钥
一顿饭一把临时钥匙，吃完作废
会话密钥与完美前向保密：旧钥匙泄露，也解不开录下的旧对话
匣底字号与商会作保的印样
数字证书与证书颁发机构（CA）：证明“这个公钥属于这个域名”
匣底字号对不上，客人当场不点
证书校验失败：浏览器报警并阻止连接，或只允许用户手动绕过
封匣只保没被偷看、没被改动、对面真是临江楼
HTTPS 的三项保护：机密性、完整性、身份认证；不保证应用本身可信
商会当场摘掉字号
证书吊销：CRL、OCSP 与短期证书

HTTP 规定的是“怎么说话”

一次 HTTP 对话只有两步：客户端发一个请求，服务器回一个响应。请求的开头是请求行——方法、路径、协议版本，例如 GET /menu HTTP/1.1；接着是头部，说明要什么格式、来自哪个站点、带了哪块熟客牌子；最后是可选的正文。响应也是三段：状态行（如 HTTP/1.1 200 OK）、响应头、响应正文。方法中，GET 是“取”，POST 是“交”，PUT/PATCH 是“改”，DELETE 是“删”。HTTP 只管格式与语义，不规定正文里装什么——HTML、JSON、图片、视频都装得下，这就是“超文本”后来能承载整个万维网的原因。

无状态：省事，也留下了麻烦

每个请求都自带足够的信息，服务器不必记得上一个请求是谁发的。好处是简单、易扩展：任何一台服务器都能接住下一个请求，坏了换一台也不丢状态。麻烦是“登录”无处安放。于是有了 Cookie——服务器在响应里塞一张小纸条，浏览器此后每次请求自动附上；常见做法是纸条上只写一个编号，真正的登录记录仍存在服务器的 Session 里。故事里那块“熟客的牌子”，就是 Cookie；柜台后头记着熟客账的本子，就是 Session。

HTTPS 不是另一种协议，是 HTTP 套了一层 TLS

请求与响应的格式一字未改，只是整段对话先经过 TLS。握手做三件事：其一，服务器出示证书，客户端逐级验到浏览器内置的受信任根证书，确认“对面真是临江楼”；其二，双方用 ECDHE 之类的方法交换材料，各自算出同一把会话密钥——这把钥匙从没在网络上明文传递过；其三，此后所有数据用对称加密传输，因为对称加密快得多。每次连接都换一把新钥匙，所以即使某天服务器私钥泄露，攻击者也解不开此前录下的对话，这叫完美前向保密。故事里“一顿饭一把临时钥匙”，说的就是它。

小锁保证什么，不保证什么

地址栏的小锁只说明两件事：这条通道是加密的，对面持有的证书与域名相符。它不说明这家网站是好人——钓鱼站同样可以申请一张合法证书，照样带锁。它也管不了服务器拿到你的密码之后怎么用。HTTPS 保护的是“传输中”，不是“服务器里”。另外，明文 HTTP 下，路径、查询串、Cookie、正文都可能被同一 Wi-Fi 下的人看见；换成 HTTPS 后这些都被封进匣子，但域名与 IP 仍可能从握手时的 SNI 或流量特征中泄露，更新的 ECH 等机制正是为了补这一处。

寓言之外：代理、缓存与重放

大堂里的托盘像代理（Proxy）：它可以转发，可以缓存——把常点的菜先备好，也可以作恶。HTTPS 让中间人只能转发、不能偷看；但若代理就是你自己部署的反向代理，TLS 在那里终止，它当然看得见内容，所以“端到端”到哪一端，要看架构。旧菜条被捡回来再递一次，是重放攻击；TLS 靠每次握手的新随机数与记录序列号，让同一段密文不能拿到另一顿饭上再用。至于 HTTP/2、HTTP/3 的多路复用与 QUIC，就像一个跑堂同时端几桌的菜、还不用排队——那是另一个层面的故事了。
